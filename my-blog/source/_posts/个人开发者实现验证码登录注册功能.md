# 个人开发者实现验证码登录注册功能

> 面向 **Web 网站（PC / H5）**，后端 **Spring Boot + Redis**，提供 **阿里云短信** 与 **QQ 邮箱 SMTP** 两条验证码通道。
>
> 个人开发者做这个功能的真正难点**不在代码**，而在「**通道资质 + 防刷成本**」。本篇按「选通道 → 设计流程 → 落地细节 → 安全防护」的顺序记录实现思路。

---

# 一、先搞清楚难点在哪

| 环节 | 个人开发者的现实约束 |
|---|---|
| 短信资质 | 阿里云短信需**实名认证**，签名与模板审核严格，个人主体可申请但类目受限 |
| 短信成本 | 按条计费，**被恶意刷验证码会直接烧钱** |
| 备案要求 | 网站域名需备案，短信签名通常要求与备案主体关联 |
| 邮箱通道 | 几乎无门槛，**QQ 邮箱开 SMTP 拿授权码即可**，但有发送频率限制 |

> **结论**：短信通道负责「正式用户」，邮箱通道负责「低成本兜底 + 开发调试」。两条通道**共用一个验证码业务层**，只是发送实现不同。

---

# 二、双通道方案设计

## （一）通道选型对比

| 对比项 | 阿里云短信 | QQ 邮箱 SMTP |
|---|---|---|
| 账号标识 | 手机号 | 邮箱地址 |
| 资质门槛 | 需实名 + 签名模板审核 | 仅需邮箱授权码 |
| 成本 | 约 0.04 元/条 | **免费** |
| 到达率 | 高 | 中（易进垃圾箱） |
| 时效性 | 秒级 | 秒级~分钟级 |
| 适用场景 | 正式对外、手机号注册 | 个人项目、调试、邮箱注册 |

## （二）统一抽象设计（关键）

不要为两条通道写两套业务逻辑。抽出一个**发送接口**，业务层只依赖接口：

```
VerificationCodeService（业务层）
    ├── 生成验证码
    ├── 频率/次数校验
    ├── 写 Redis
    ├── 校验验证码
    └── 调用 SmsSender 发送

SmsSender（发送接口）
    ├── AliyunSmsSender   → 手机号
    └── EmailSmsSender    → 邮箱
```

**设计要点**：

- 通道差异**只在发送实现**，业务层的限流、校验、存储逻辑完全复用
- 通过 `type` 字段区分通道（`PHONE` / `EMAIL`），或直接按目标标识格式自动路由
- 新增通道（如微信小程序）时只加一个实现类，**符合开闭原则**

## （三）阿里云短信要点

- 控制台先申请**签名**（如「XX 商城」）和**模板**（如 `您的验证码为 ${code}，5 分钟内有效`）
- 模板变量用 `${code}` 占位，代码里传 `Map<String, String>` 填充
- 调用官方 SDK：`com.aliyun:aliyun-java-sdk-core` + `dysmsapi`
- 核心参数：`PhoneNumbers`、`SignName`、`TemplateCode`、`TemplateParam`
- **Region 与 Endpoint 要匹配**（如 `cn-hangzhou` → `dysmsapi.aliyuncs.com`）
- AccessKey 建议用 **RAM 子账号**，只授予 `AliyunDysmsFullAccess`，不要用主账号 AK

## （四）QQ 邮箱 SMTP 要点

- QQ 邮箱 → 设置 → 账户 → 开启 **SMTP 服务**，获取**授权码**（不是登录密码）
- Spring Boot 引入 `spring-boot-starter-mail`
- 配置项：

```yaml
spring:
  mail:
    host: smtp.qq.com
    port: 465
    username: xxx@qq.com
    password: 授权码
    properties:
      mail:
        smtp:
          auth: true
          ssl:
            enable: true
```

- 465 端口走 **SSL**，587 走 STARTTLS，**选一个配对应开关**
- 用 `JavaMailSender` 发 `SimpleMailMessage`，HTML 内容用 `MimeMessageHelper`
- QQ 邮箱对**单日发送量**和**发送频率**有隐性限制，避免短时间群发

# 三、整体流程设计

## （一）发送验证码流程

```
前端输入手机号/邮箱
      ↓
POST /auth/code/send
      ↓
① 图形验证码/滑块校验（人机校验）
      ↓
② 目标格式校验（正则）
      ↓
③ 频率校验
   ├─ 同一目标 60s 内只发一次
   ├─ 同一 IP 每小时上限（如 10 次）
   └─ 同一目标 每日上限（如 10 次）
      ↓
④ 生成 6 位数字验证码（SecureRandom）
      ↓
⑤ 写入 Redis（TTL 5 分钟）
      ↓
⑥ 调用对应通道发送
      ↓
返回「发送成功」（不返回验证码本身）
```

> **重点**：步骤 ①③ **必须在步骤 ⑥ 之前**，否则刷接口就能白嫖短信费用。

## （二）登录/注册合一流程

```
前端提交：目标标识 + 验证码
      ↓
POST /auth/login
      ↓
① 从 Redis 取验证码
   ├─ 不存在 → 已过期/未发送
   └─ 不匹配 → 累计失败次数，超限锁定
      ↓
② 匹配成功 → 立即删除该 key（一次性消费）
      ↓
③ 查用户表：该手机号/邮箱是否存在
   ├─ 存在   → 登录
   └─ 不存在 → 自动注册（补昵称、初始状态）
      ↓
④ 签发凭证（JWT / Session）
      ↓
返回 token + 用户信息
```

> **设计亮点**：**登录注册合并**，用「验证码通过后判断用户是否存在」替代两套接口。用户体验上少一个页面，代码上也少一套逻辑。

## （三）已有账号绑定关系

建议用户表这样设计：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `phone` | 手机号，允许 `null`，**唯一索引** |
| `email` | 邮箱，允许 `null`，**唯一索引** |
| `nickname` | 昵称，首次注册自动生成 |
| `status` | 状态（正常 / 禁用） |
| `create_time` | 创建时间 |

> **要点**：`phone` 和 `email` 分别建**唯一索引**（注意 MySQL 中多个 `NULL` 不冲突，可放心允许空值）。这样同一用户后续可以绑定另一通道，实现「手机号或邮箱任选一种登录」。

# 四、Redis 数据结构设计

这是整个功能的核心，**键的设计决定了防护是否到位**：

| Key | Value | TTL | 作用 |
|---|---|---|---|
| `auth:code:{type}:{target}` | 验证码 | 5 分钟 | 存储验证码 |
| `auth:send:cd:{type}:{target}` | `1` | 60 秒 | 防重复发送（发送冷却） |
| `auth:send:ip:{ip}` | 计数 | 1 小时 | 单 IP 发送上限 |
| `auth:send:daily:{type}:{target}` | 计数 | 到次日 0 点 | 单个目标当日上限 |
| `auth:fail:{type}:{target}` | 失败次数 | 10 分钟 | 校验失败锁定 |

**关键实现细节**：

- **TTL 而非定时任务**：验证码过期交给 Redis 自动清理，不需要定时任务扫描
- **发送冷却**：写 `auth:send:cd` 并设 60s TTL，写入前先判断是否存在（`SETNX` 天然实现分布式互斥）
- **失败计数**：校验失败时 `INCR`，达到阈值（如 5 次）后**删除验证码 key 并锁定**
- **一次性消费**：校验成功后**立刻 `DEL`**，防止同一验证码被重放

> **易错点**：不要用「查询后删除」，高并发下有竞态。可用 Lua 脚本把「比对 + 删除」做成原子操作，或用 `GETDEL`（Redis 6.2+）。

# 五、安全防护

## （一）必须做的防护

| 防护措施 | 说明 |
|---|---|
| **图形验证码前置** | 滑块 / 图片验证码，挡住脚本刷接口 |
| **发送频率限制** | 60s 冷却 + 每日上限 + IP 上限，三层限流 |
| **验证码有效期** | 5 分钟，不宜过长 |
| **一次性消费** | 校验成功立即删除 |
| **失败次数锁定** | 连续错 5 次锁 10 分钟，防暴力枚举 |
| **验证码强度** | 6 位随机数字，用 `SecureRandom` 而非 `Random` |
| **接口返回统一** | 不暴露「手机号是否已注册」，防用户枚举 |
| **账户余额告警** | 阿里云设置**费用告警**，异常消耗及时发现 |

## （二）容易被忽视的点

- **不要在前端存验证码**，也不要返回验证码（哪怕是测试环境，容易忘删）
- **验证码日志脱敏**：日志里不要打印完整验证码和手机号
- **HTTPS 必须开启**：否则验证码在传输中可能被截获
- **JWT 密钥**不要硬编码，放配置中心或环境变量
- **同一 IP 大量失败**时也应有告警，可能是撞库攻击

## （三）防刷思路（进阶）

```
限流维度：
  ├─ 目标维度：同一手机号/邮箱
  ├─ IP 维度：同一来源 IP
  ├─ 设备维度：前端生成的设备指纹
  └─ 全局维度：整个接口的 QPS 上限
```

个人项目至少要做到**目标 + IP 两个维度**，配合图形验证码，基本能挡住 90% 的脚本攻击。

# 六、接口设计

## （一）发送验证码

```
POST /auth/code/send
```

| 参数 | 说明 |
|---|---|
| `target` | 手机号或邮箱 |
| `type` | `PHONE` / `EMAIL` |
| `captchaToken` | 图形验证码通过后返回的 token |

**返回**：只返回成功/失败，**不返回验证码**。

## （二）登录/注册

```
POST /auth/login
```

| 参数 | 说明 |
|---|---|
| `target` | 手机号或邮箱 |
| `type` | `PHONE` / `EMAIL` |
| `code` | 验证码 |

**返回**：`token`、`userId`、`nickname`、`isNewUser`（是否新注册）。

> `isNewUser` 很有用：前端可以据此引导「完善资料」或跳转不同页面。

## （三）其他建议接口

| 接口 | 作用 |
|---|---|
| `POST /auth/logout` | 退出登录 |
| `POST /auth/bind` | 绑定另一通道（手机号 ↔ 邮箱） |
| `GET /auth/me` | 获取当前用户信息 |

# 七、前端配合要点

- **发送按钮倒计时 60s**，与后端冷却时间保持一致，避免用户点击报错
- 请求中加 **loading 状态**，防止重复点击
- 验证码输入框限制 **6 位数字**，`inputmode="numeric"` 唤起数字键盘
- 图形验证码**失败后自动刷新**
- token 存储：Web 建议 **HttpOnly Cookie**（防 XSS 窃取），若要放 localStorage，需配合 XSS 防护

---

# 八、落地顺序建议

个人项目按这个顺序推进，能最快跑通闭环：

| 阶段 | 内容 | 说明 |
|---|---|---|
| 1 | **先做邮箱通道** | 零门槛、免费，先把整个流程跑通 |
| 2 | 接入 Redis 限流与校验 | 完善防刷与一次性消费 |
| 3 | 登录注册合一 + JWT 签发 | 打通用户体系 |
| 4 | 接入阿里云短信 | 申请签名模板，替换发送实现 |
| 5 | 图形验证码 + 多维度限流 | 上线前必备 |
| 6 | 监控告警 | 阿里云费用告警、失败率告警 |

> **核心思路**：**先用邮箱通道把业务流程全部跑通，再接短信通道**。因为两条通道共用业务层，切换成本几乎为零，但短信的资质审核可能需要几天，不应该阻塞开发。

# 九、总结

| 模块 | 核心要点 |
|---|---|
| 通道选择 | 短信走阿里云，邮箱走 QQ SMTP，**业务层统一抽象** |
| 流程设计 | 发送前先人机校验 + 限流；**登录注册合一** |
| Redis | 验证码 TTL 5min、60s 冷却、失败计数、**一次性消费** |
| 安全防护 | 三层限流 + 失败锁定 + 图形验证码 + 费用告警 |
| 落地顺序 | **先邮箱跑通流程，后接短信上线** |

**易错清单**：

1. **限流必须在发短信之前**，否则接口被刷会直接产生费用
2. **验证码校验成功后必须立即删除**，防止重放
3. **不要用 `Random` 生成验证码**，要用 `SecureRandom`
4. **AccessKey 用 RAM 子账号**，权限最小化
5. **QQ 邮箱要用授权码**，不是登录密码
6. **`phone` / `email` 字段分别建唯一索引**，并允许 `NULL`
7. **日志中不要打印完整验证码和手机号**
8. **接口不要暴露「账号是否已注册」**，防用户枚举
