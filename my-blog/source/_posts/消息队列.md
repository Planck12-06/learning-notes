# 消息队列

> 前半部分以优惠券秒杀为主线，从同步下单逐步演进到 Redis Stream 异步下单，理解消息队列解决什么问题；
> 后半部分为 RabbitMQ 的使用与消息可靠性保障。

## 一、消息队列概述

### 1.1 同步调用与异步调用

以支付业务为例：用户支付成功后，支付服务需要依次调用订单服务修改订单状态、调用短信服务发送通知、调用积分服务增加积分。这种**同步调用**存在三个问题：

- **拓展性差**：每增加一个下游需求，都需要修改上游代码、新增一次调用，不符合开闭原则
- **性能下降**：每一步都需阻塞等待上一步返回，链路总耗时为各服务耗时之和，线程全程阻塞
- **级联失败**：链路中任一服务故障，都会导致整条链路失败，并可能拖垮上游服务

**异步调用**把直接调用改为消息通知，引入三个角色：

- **消息发送者**：原调用方，只负责把消息投递出去
- **消息代理（Broker）**：暂存、转发消息
- **消息接收者**：原服务提供方，按需获取并处理消息

异步调用的优势：

- **解除耦合**：新增下游需求只需增加订阅，上游代码无需改动
- **性能提升**：上游无需等待下游全部处理完成
- **故障隔离**：单个消费者故障不影响上游与其它服务
- **流量削峰**：消息先堆积在 Broker，消费者按自身处理能力匀速消费

异步调用的代价：

- 无法立即得到调用结果，时效性差
- 不确定下游业务是否执行成功
- 业务可靠性依赖于 Broker 的可靠性

### 1.2 消息模型

**消息队列（Message Queue）** 即存放消息的队列，最简单的模型包含三个角色：

- **消息队列（Broker）**：存储和管理消息，也称消息代理
- **生产者（publisher）**：发送消息到消息队列
- **消费者（consumer）**：从消息队列获取消息并处理消息

```
生产者 ──发送──▶ 消息队列（Broker）──派发──▶ 消费者
```

生产者只需把消息交给 Broker，不必关心谁来处理、何时处理；消费者按各自节奏拉取处理，由此实现**解耦**与**异步**。映射到秒杀场景：主线程作为生产者把订单消息写入队列，后台线程作为消费者异步落库，从而削峰填谷、保护数据库。

### 1.3 技术选型

| | RabbitMQ | ActiveMQ | RocketMQ | Kafka |
|---|---|---|---|---|
| 公司/社区 | Rabbit | Apache | 阿里 | Apache |
| 开发语言 | Erlang | Java | Java | Scala & Java |
| 协议支持 | AMQP、XMPP、SMTP、STOMP | OpenWire、STOMP、AMQP | 自定义协议 | 自定义协议 |
| 可用性 | 高 | 一般 | 高 | 高 |
| 单机吞吐量 | 一般 | 差 | 高 | 非常高 |
| 消息延迟 | 微秒级 | 毫秒级 | 毫秒级 | 毫秒以内 |
| 消息可靠性 | 高 | 一般 | 高 | 一般 |

- 追求可靠性与功能完善：RabbitMQ
- 追求海量吞吐与流处理：Kafka
- 兼顾吞吐与功能（事务消息、延迟消息等）：RocketMQ

## 二、秒杀场景与方案演进概览

秒杀的核心挑战：**高并发下防止超卖、保证一人一单，同时不让数据库被瞬时流量打垮**。

围绕这一挑战，方案经历了三次演进：

| 方案 | 核心思路 | 主要缺陷 |
|---|---|---|
| **悲观锁**（同步） | 加锁串行化下单，数据库层校验 | 集群下锁失效、全流程同步阻塞，性能差 |
| **阻塞队列**（JVM 异步） | Lua 预检 + JVM 内存队列异步落库 | 宕机丢消息、无 ACK、有内存溢出风险 |
| **Redis Stream**（最终方案） | Lua 预检 + Redis 消息队列异步落库 | 实现略复杂，但可靠、可扩展 |

## 三、方案一：悲观锁实现优惠券秒杀

### 3.1 实现思路

最直观的做法：在数据库层面完成所有校验（时间、库存、一人一单），用 **悲观锁**（`synchronized`，基于用户 ID 加锁）保证同一用户的并发请求串行执行，再通过事务方法落库。

### 3.2 核心代码

```java
@Override
public Result seckillVoucher(Long voucherId) {
    // 1. 查询优惠券
    SeckillVoucher voucher = seckillVoucherService.getById(voucherId);
    // 2. 判断秒杀是否开始
    if (voucher.getBeginTime().isAfter(LocalDateTime.now())) {
        return Result.fail("秒杀尚未开始");
    }
    // 3. 判断秒杀是否结束
    if (voucher.getEndTime().isBefore(LocalDateTime.now())) {
        return Result.fail("秒杀已结束");
    }
    // 4. 判断库存是否充足
    if (voucher.getStock() < 1) {
        return Result.fail("库存不足");
    }
    // 5. 一人一单：基于用户 ID 加悲观锁（单机版）
    Long userId = UserHolder.getUser().getId();
    synchronized (userId.toString().intern()) {
        // 获取代理对象调用事务方法，避免 @Transactional 失效
        IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
        return proxy.createVoucherOrder(voucherId);
    }
}

/**
 * 创建订单并落库（事务方法）：一人一单查重 + 乐观锁扣库存 + 保存订单
 */
@Transactional
public Result createVoucherOrder(Long voucherId) {
    Long userId = UserHolder.getUser().getId();

    // 1. 一人一单校验
    int count = query().eq("user_id", userId).eq("voucher_id", voucherId).count();
    if (count > 0) {
        return Result.fail("不允许重复下单");
    }

    // 2. 扣减库存（乐观锁：stock > 0 才更新）
    boolean success = seckillVoucherService.update()
            .setSql("stock = stock - 1")
            .eq("voucher_id", voucherId)
            .gt("stock", 0)
            .update();
    if (!success) {
        return Result.fail("库存不足");
    }

    // 3. 保存订单
    VoucherOrder voucherOrder = new VoucherOrder();
    voucherOrder.setId(redisIdWorker.nextId("order"));
    voucherOrder.setUserId(userId);
    voucherOrder.setVoucherId(voucherId);
    save(voucherOrder);
    return Result.ok(voucherOrder.getId());
}
```

### 3.3 存在的问题

- **集群失效**：`synchronized` 是 JVM 级锁，集群部署时各实例各自加锁，一人一单被击穿（可升级为 Redisson 分布式锁，参见 {% post_link 分布式锁 分布式锁 %} 笔记）
- **同步阻塞**：即使换成分布式锁，整个下单流程仍是**同步调用**——所有请求都要排队走数据库查重、扣减、插入，高并发下大量线程阻塞，吞吐量低

> **优化方向**：把"校验"前移到 Redis（Lua 脚本原子判断），把"落库"变成后台异步执行——这就引出了**异步下单**思想。

## 四、方案二：阻塞队列实现优惠券秒杀

### 4.1 实现思路

将同步流程拆为两段：

- **主线程**：执行 Lua 脚本，在 Redis 中**原子**完成时间/库存/一人一单校验，通过后立即返回订单 ID（响应极快）
- **后台线程**：从 JVM 内的 `BlockingQueue` 中取出订单，加分布式锁兜底后异步落库

```
用户请求 ──▶ Lua 原子校验（Redis）──▶ 放入阻塞队列 ──▶ 立即返回订单ID
                                          │
                                          ▼
                              后台线程 take 订单 ──▶ 加锁 + 事务落库
```

### 4.2 核心代码

```java
/** 阻塞队列：存放待处理的订单（容量 1024 * 1024） */
private BlockingQueue<VoucherOrder> orderTasks = new ArrayBlockingQueue<>(1024 * 1024);

/** 单线程线程池：用于异步消费队列中的订单 */
private static final ExecutorService SECKILL_ORDER_EXECUTOR = Executors.newSingleThreadExecutor();

/** 秒杀下单 Lua 脚本：原子校验库存、一人一单 */
private static final DefaultRedisScript<Long> SECKILL_SCRIPT;

/** 存放当前请求的 AOP 代理对象，供后台线程调用事务方法 */
private IVoucherOrderService proxy;

static {
    SECKILL_SCRIPT = new DefaultRedisScript<>();
    SECKILL_SCRIPT.setLocation(new ClassPathResource("seckill.lua"));
    SECKILL_SCRIPT.setResultType(Long.class);
}

/**
 * Bean 初始化后启动订单消费线程
 */
@PostConstruct
private void init() {
    SECKILL_ORDER_EXECUTOR.submit(new VoucherOrderHandler());
}

/**
 * 秒杀下单入口（阻塞队列版）
 */
@Override
public Result seckillVoucher(Long voucherId) {
    Long userId = UserHolder.getUser().getId();
    Long orderId = redisIdWorker.nextId("order");

    // 1. 执行 Lua 脚本：原子校验库存、一人一单
    //    返回值：0=成功，1=库存不足，2=重复下单
    Long result = stringRedisTemplate.execute(
            SECKILL_SCRIPT,
            Collections.emptyList(),
            voucherId.toString(),
            userId.toString(),
            String.valueOf(orderId)
    );
    int r = result.intValue();
    if (r != 0) {
        return Result.fail(r == 1 ? "库存不足" : "不允许重复下单");
    }

    // 2. 构造订单对象
    VoucherOrder voucherOrder = new VoucherOrder();
    voucherOrder.setId(orderId);
    voucherOrder.setUserId(userId);
    voucherOrder.setVoucherId(voucherId);

    // 3. 保存代理对象，供后台线程调用事务方法（避免事务失效）
    proxy = (IVoucherOrderService) AopContext.currentProxy();

    // 4. 放入阻塞队列，由后台线程异步落库
    orderTasks.add(voucherOrder);

    // 5. 立即返回订单ID
    return Result.ok(orderId);
}

/**
 * 后台处理订单：Redisson 分布式锁兜底一人一单，再调用事务方法落库
 */
private void handleVoucherOrder(VoucherOrder voucherOrder) {
    Long userId = voucherOrder.getUserId();
    RLock lock = redissonClient.getLock("lock:order:" + userId);
    boolean isLock = lock.tryLock();
    if (!isLock) {
        log.error("不允许重复下单, userId={}", userId);
        return;
    }
    try {
        // 通过代理调用，确保 @Transactional 生效
        proxy.createVoucherOrder(voucherOrder);
    } finally {
        lock.unlock();
    }
}

/**
 * 创建订单并落库（事务方法）
 */
@Transactional
public void createVoucherOrder(VoucherOrder voucherOrder) {
    Long userId = voucherOrder.getUserId();
    Long voucherId = voucherOrder.getVoucherId();

    // 1. 一人一单兜底校验
    int count = query().eq("user_id", userId).eq("voucher_id", voucherId).count();
    if (count > 0) {
        return;
    }

    // 2. 乐观锁扣减库存（stock > 0 才更新）
    boolean success = seckillVoucherService.update()
            .setSql("stock = stock - 1")
            .eq("voucher_id", voucherId)
            .gt("stock", 0)
            .update();
    if (!success) {
        return;
    }

    // 3. 保存订单
    save(voucherOrder);
}

/**
 * 阻塞队列版订单消费任务
 */
private class VoucherOrderHandler implements Runnable {
    @Override
    public void run() {
        while (true) {
            try {
                // 阻塞获取订单（队列空时阻塞等待）
                VoucherOrder voucherOrder = orderTasks.take();
                handleVoucherOrder(voucherOrder);
            } catch (Exception e) {
                log.error("处理阻塞队列订单失败", e);
            }
        }
    }
}
```

### 4.3 存在的问题

- **宕机丢消息**：订单存放在 **JVM 内存**中，服务宕机或重启，队列里未消费的订单**全部丢失**
- **无确认机制**：后台线程取出订单后若处理失败，消息无法重试（没有 ACK）
- **不支持多实例**：队列在单机 JVM 内，无法多个实例共同消费
- **内存溢出风险**：队列容量有限（`1024 * 1024`），秒杀流量过大时可能 OOM

> **根因**：需要一个 **独立于 JVM、可持久化、支持消费确认（ACK）** 的队列——这正是 **消息队列（Message Queue）** 的定义。Redis 恰好提供了这样的能力。

## 五、Redis 实现消息队列的三种方式

上面的阻塞队列方案，根子上缺的是一个**独立于 JVM、可持久化、支持消费确认（ACK）** 的队列。Redis 恰好提供了三种实现消息队列的方式：

| 方式 | 特点 | 适用场景 |
|---|---|---|
| **List 结构** | 基于 List 模拟消息队列 | 简单的任务队列 |
| **PubSub** | 发布/订阅消息模型 | 实时消息广播 |
| **Stream** | 完善的消息队列模型 | 生产级可靠消息队列（推荐） |

### 5.1 基于 List 结构模拟消息队列

使用 `LPUSH` 从一端写入、`RPOP` 从另一端读取，天然符合"队列"语义：

```bash
# 生产者（左入）
LPUSH mq:order 1001

# 消费者（右出）
RPOP mq:order
```

- **优点**：借助 Redis 持久化，消息可落地；满足有序性
- **缺点**：不支持广播；**没有 ACK 机制**，消费者取走消息后宕机则消息丢失

### 5.2 基于 PubSub 实现消息队列

发布/订阅模型：发布者向频道发消息，所有订阅者都能收到：

```bash
# 订阅者
SUBSCRIBE mq:order

# 发布者
PUBLISH mq:order "order created: 1001"
```

- **优点**：支持多消费者广播，实时性高
- **缺点**：**不支持持久化**，Redis 重启或订阅者离线期间的消息全部丢失；消息堆积无上限；没有 ACK

### 5.3 基于 Stream 实现消息队列

Stream 是 Redis 5.0 引入的**专门的消息队列数据结构**，弥补了 List 与 PubSub 的不足，是 Redis 中最完善的方案。

**核心概念**：

- **Consumer Group（消费组）**：组内多个消费者共同消费，**每条消息只被组内一个消费者处理**（负载均衡）
- **last_delivered_id**：消费组记录消费位置，避免重复消费
- **Pending List（待确认列表）**：记录已投递但**未 ACK** 的消息，消费者宕机后可重新派发

**常用命令**：

```bash
# 生产消息
XADD mq:order * name "phone" userId 1001

# 创建消费组
XGROUP CREATE mq:order g1 0

# 消费者读取消息（BLOCK 2000 表示最多阻塞 2 秒）
XREADGROUP GROUP g1 c1 COUNT 1 BLOCK 2000 STREAMS mq:order >

# 消费者处理完成后 ACK 确认
XACK mq:order g1 1692345678901-0
```

**优点**：消息可持久化、可回溯；消费组支持负载均衡；**有 ACK 机制**，失败可重试；支持消息堆积管理。

### 5.4 三种方式对比

| 对比项 | List | PubSub | Stream |
|---|---|---|---|
| 消息持久化 | ✅ | ❌ | ✅ |
| 消息回溯 | ❌ | ❌ | ✅ |
| 多消费者 | ❌（竞争消费） | ✅（广播） | ✅（消费组） |
| 消息确认（ACK） | ❌ | ❌ | ✅ |
| 阻塞读取 | ✅（`BRPOP`） | ✅（订阅） | ✅（`XREADGROUP BLOCK`） |

> **结论**：Stream 具备持久化 + 消费组 + ACK + pending-list 重试，恰好逐一化解阻塞队列方案的全部缺陷。因此秒杀最终方案选用 **Redis Stream**。

## 六、方案三：Redis Stream 实现优惠券秒杀

### 6.1 实现思路

与阻塞队列方案相比，整体链路不变，只把"JVM 内存队列"替换为"Redis Stream"：

1. 请求到达 `seckillVoucher`，执行 Lua 脚本：**原子**校验时间、库存、一人一单，**并将订单消息写入 Redis Stream**（校验 + 入队一步完成）
2. 后台线程以消费组（`g1/c1`）从 Stream 读取订单，Redisson 分布式锁兜底，异步落库
3. 处理成功后 `XACK` 确认；处理失败的消息留在 **pending-list**，由 `handlePendingList` 重试

```
用户请求 ──▶ Lua 原子校验 + XADD 写入 Stream ──▶ 立即返回订单ID
                        │
                        ▼
        后台线程消费组读取 ──▶ 处理成功：XACK 确认
                        └──▶ 处理失败：进入 pending-list，重试
```

### 6.2 完整代码

```java
/**
 * <p>
 * 优惠券订单服务实现类
 * </p>
 * <p>
 * 秒杀下单采用「Lua脚本原子校验 + Redis Stream 异步下单」方案：
 * <ol>
 *     <li>请求到达 seckillVoucher，执行 Lua 脚本：校验时间、库存、一人一单，并将订单写入 Redis Stream</li>
 *     <li>后台线程从 Stream 消费订单，使用 Redisson 分布式锁做兜底，再异步落库</li>
 *     <li>消费失败的消息进入 pending-list，由 handlePendingList 重试</li>
 * </ol>
 */
@Slf4j
@Service
public class VoucherOrderServiceImpl extends ServiceImpl<VoucherOrderMapper, VoucherOrder> implements IVoucherOrderService {

    /** 秒杀券服务：用于扣减库存等操作 */
    @Resource
    private ISeckillVoucherService seckillVoucherService;

    /** Redis 全局唯一ID生成器 */
    @Resource
    private RedisIdWorker redisIdWorker;

    /** Redisson 客户端：用于分布式锁兜底 */
    @Resource
    private RedissonClient redissonClient;

    /** Redis 操作模板：用于执行 Lua 脚本、操作 Stream */
    @Resource
    private StringRedisTemplate stringRedisTemplate;

    /** 存放当前请求的 AOP 代理对象，供后台线程调用事务方法 */
    private IVoucherOrderService proxy;

    /** Redis Stream 名称 */
    private final String queueName = "stream.orders";

    /** 秒杀下单 Lua 脚本：原子性校验库存、一人一单，并写入 Stream */
    private static final DefaultRedisScript<Long> SECKILL_SCRIPT;

    /** 单线程线程池：用于异步消费 Stream 中的订单消息 */
    private static final ExecutorService SECKILL_ORDER_EXECUTOR = Executors.newSingleThreadExecutor();

    static {
        // 加载 classpath 下的 seckill.lua 脚本
        SECKILL_SCRIPT = new DefaultRedisScript<>();
        SECKILL_SCRIPT.setLocation(new ClassPathResource("seckill.lua"));
        SECKILL_SCRIPT.setResultType(Long.class);
    }

    /**
     * Bean 初始化后启动订单消费线程
     */
    @PostConstruct
    private void init() {
        // 先创建 Stream 和消费者组（key 不存在则自动创建）
        try {
            stringRedisTemplate.opsForStream().createGroup(queueName, "g1");
        } catch (RedisSystemException e) {
            // 组已存在会抛 BUSYGROUP，忽略即可；其它异常可记录
            if (!e.getMessage().contains("BUSYGROUP")) {
                log.warn("创建消费组异常", e);
            }
        }
        SECKILL_ORDER_EXECUTOR.submit(new VoucherOrderHandler());
    }

    /**
     * 秒杀下单入口（异步方案）
     * <p>
     * 1. 生成订单ID<br>
     * 2. 执行 Lua 脚本：校验时间/库存/一人一单，通过则将订单写入 Redis Stream<br>
     * 3. 保存当前代理对象，供后台消费线程调用 createVoucherOrder（事务方法）<br>
     * 4. 直接返回订单ID，落库由后台线程异步完成
     */
    @Override
    public Result seckillVoucher(Long voucherId) {
        // 1. 生成全局唯一订单ID
        Long orderId = redisIdWorker.nextId("order");

        // 2. 执行 Lua 脚本：原子校验并写入 Stream
        //    返回值：0=成功，1=库存不足，2=重复下单
        Long result = stringRedisTemplate.execute(
                SECKILL_SCRIPT,
                Collections.emptyList(),
                voucherId.toString(),
                UserHolder.getUser().getId().toString(),
                String.valueOf(orderId)
        );
        int r = result.intValue();
        if (r != 0) {
            return Result.fail(r == 1 ? "库存不足" : "不允许重复下单");
        }

        // 3. 保存代理对象，供后台线程调用事务方法（避免事务失效）
        proxy = (IVoucherOrderService) AopContext.currentProxy();

        // 4. 返回订单ID
        return Result.ok(orderId);
    }

    /**
     * 后台处理订单：使用 Redisson 分布式锁兜底一人一单，再调用事务方法落库
     */
    private void handleVoucherOrder(VoucherOrder voucherOrder) {
        Long userId = voucherOrder.getUserId();
        RLock lock = redissonClient.getLock("lock:order:" + userId);
        boolean isLock = lock.tryLock();
        if (!isLock) {
            log.error("不允许重复下单, userId={}", userId);
            return;
        }
        try {
            // 通过代理调用，确保 @Transactional 生效
            proxy.createVoucherOrder(voucherOrder);
        } finally {
            lock.unlock();
        }
    }

    /**
     * 创建订单并落库（事务方法）
     * <p>
     * 1. 一人一单兜底校验<br>
     * 2. 乐观锁扣减库存（stock > 0）<br>
     * 3. 保存订单
     */
    @Transactional
    public void createVoucherOrder(VoucherOrder voucherOrder) {
        Long userId = voucherOrder.getUserId();
        Long voucherId = voucherOrder.getVoucherId();

        // 1. 一人一单兜底校验
        int count = query()
                .eq("user_id", userId)
                .eq("voucher_id", voucherId)
                .count();
        if (count > 0) {
            log.error("不允许重复下单, userId={}, voucherId={}", userId, voucherId);
            return;
        }

        // 2. 扣减库存（乐观锁：stock > 0 才更新）
        boolean success = seckillVoucherService.update()
                .setSql("stock = stock - 1")
                .eq("voucher_id", voucherId)
                .gt("stock", 0)
                .update();
        if (!success) {
            log.error("库存不足, voucherId={}", voucherId);
            return;
        }

        // 3. 保存订单
        save(voucherOrder);
    }

    /**
     * Stream 订单消费任务
     * <p>
     * 以消费者组 g1 / 消费者 c1 持续从 Stream 读取订单消息并处理；
     * 处理失败（如消费者宕机重启后）会进入 pending-list 重试机制。
     */
    private class VoucherOrderHandler implements Runnable {

        /**
         * 主消费循环：从 Stream 读取最新未消费消息
         */
        @Override
        public void run() {
            while (true) {
                try {
                    // 阻塞读取 1 条消息（最多阻塞 2 秒）
                    List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(
                            Consumer.from("g1", "c1"),
                            StreamReadOptions.empty().count(1).block(Duration.ofSeconds(2)),
                            StreamOffset.create(queueName, ReadOffset.lastConsumed())
                    );
                    if (list == null || list.isEmpty()) {
                        continue;
                    }
                    // 解析消息并处理
                    MapRecord<String, Object, Object> record = list.get(0);
                    Map<Object, Object> values = record.getValue();
                    VoucherOrder voucherOrder = BeanUtil.fillBeanWithMap(values, new VoucherOrder(), true);
                    handleVoucherOrder(voucherOrder);
                    // 处理成功后 ACK 确认
                    stringRedisTemplate.opsForStream().acknowledge(queueName, "g1", record.getId());
                } catch (Exception e) {
                    log.error("处理秒杀订单失败", e);
                    // 异常时进入 pending-list 重试未确认的消息
                    handlePendingList();
                }
            }
        }

        /**
         * pending-list 重试机制
         * <p>
         * 读取已读取但未 ACK 确认的消息（即消费失败的消息）并重新处理，
         * 直到 pending-list 为空则退出，回到主消费循环。
         */
        private void handlePendingList() {
            while (true) {
                try {
                    // 从 pending-list 读取（ReadOffset.from("0") 表示读取未确认的消息）
                    List<MapRecord<String, Object, Object>> list = stringRedisTemplate.opsForStream().read(
                            Consumer.from("g1", "c1"),
                            StreamReadOptions.empty().count(1),
                            StreamOffset.create(queueName, ReadOffset.from("0"))
                    );
                    if (list == null || list.isEmpty()) {
                        // pending-list 为空，退出重试
                        break;
                    }
                    MapRecord<String, Object, Object> record = list.get(0);
                    Map<Object, Object> values = record.getValue();
                    VoucherOrder voucherOrder = BeanUtil.fillBeanWithMap(values, new VoucherOrder(), true);
                    handleVoucherOrder(voucherOrder);
                    stringRedisTemplate.opsForStream().acknowledge(queueName, "g1", record.getId());
                } catch (Exception e) {
                    log.error("处理 pending-list 失败", e);
                    // 失败后休眠 1 秒，避免死循环打满 CPU
                    try {
                        Thread.sleep(1000);
                    } catch (InterruptedException ex) {
                        Thread.currentThread().interrupt();
                        throw new RuntimeException(ex);
                    }
                }
            }
        }
    }
}
```

### 6.3 要点小结

- **防超卖**：Lua 脚本把"校验 + 写入 Stream"做成**原子操作**，判断与写入之间不会有并发缝隙
- **可靠性**：消息存于 Redis（可持久化），服务宕机重启后从 pending-list 恢复未确认消息，**不丢单**
- **不重复**：消费组记录消费位置 + `XACK` 确认 + Redisson 锁 + 数据库查重，多重保障一人一单
- **高性能**：主线程只与 Redis 交互即返回，数据库压力被削峰

## 七、三种方案总结

| 对比项 | 悲观锁 | 阻塞队列 | Redis Stream |
|---|---|---|---|
| 集群可用 | ❌（JVM 锁） | ✅ | ✅ |
| 异步下单 | ❌（同步阻塞） | ✅ | ✅ |
| 宕机不丢消息 | — | ❌（JVM 内存丢失） | ✅（Redis 持久化 + pending-list） |
| 消费确认（ACK） | — | ❌ | ✅ |
| 多实例消费 | — | ❌ | ✅（消费组） |
| 数据库压力 | 大（全量请求打库） | 小（Redis 预检 + 异步落库） | 小（同左，且更可靠） |

> 演进的本质：**把"判断"不断前移（数据库 → Redis Lua），把"写库"不断后置（同步 → JVM 队列 → Redis Stream）**。
>
> Redis Stream 能解决单一业务内的异步削峰，但不具备复杂路由、多语言客户端、完善的管理控制台等能力。在微服务架构中做服务间解耦，通常仍会使用专业消息中间件，下面以 RabbitMQ 为例。

## 八、RabbitMQ 基础

### 8.1 安装部署与核心概念

```bash
docker run \
  -e RABBITMQ_DEFAULT_USER=itheima \
  -e RABBITMQ_DEFAULT_PASS=123321 \
  -v mq-plugins:/plugins \
  --name mq \
  --hostname mq \
  -p 15672:15672 \
  -p 5672:5672 \
  --network hm-net \
  -d \
  rabbitmq:3.8-management
```

- `5672`：客户端通信端口
- `15672`：管理控制台端口，浏览器访问 `http://虚拟机IP:15672`
- `mq-plugins`：插件目录的数据卷，安装延迟消息插件时会用到
- `--network hm-net`：加入自定义网络（黑马商城项目使用），无此需求时可去掉

**核心概念**：

- `publisher`：生产者，发消息的一方
- `consumer`：消费者，处理消息的一方
- `queue`：队列，存消息。生产者投递的消息暂存在队列里等消费者来取
- `exchange`：交换机，负责路由消息。**只转发不存储**，所以路由不到队列的消息是直接丢掉的
- `virtual-host`：虚拟主机，把 exchange、queue 隔离开

### 8.2 数据隔离

不同 vhost 之间数据完全隔离，即使是超级管理员，也无法访问不属于自己 vhost 的资源。

通常按项目或环境创建 vhost（如 `/hmall`），再创建对应用户（如 `hmall`），把该 vhost 的权限授权给此用户，客户端连接时指定 vhost：

```yaml
spring:
  rabbitmq:
    host: 192.168.150.101
    port: 5672
    virtual-host: /hmall
    username: hmall
    password: 123
```

这样即使队列同名，在不同 vhost 中也不会冲突。

### 8.3 SpringAMQP 收发消息

AMQP 是一套跨语言的消息协议，SpringAMQP 是 Spring 基于 AMQP 协议的封装（底层实现为 RabbitMQ），使用分为四步：

① 引依赖

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>
```

② 配置 MQ 地址（publisher 和 consumer 都要配）

③ 发消息：`RabbitTemplate`

```java
@SpringBootTest
public class SpringAmqpTest {

    @Autowired
    private RabbitTemplate rabbitTemplate;

    @Test
    public void testSimpleQueue() {
        String queueName = "simple.queue";
        String message = "hello, spring amqp!";
        rabbitTemplate.convertAndSend(queueName, message);
    }
}
```

④ 收消息：`@RabbitListener`

```java
@Component
public class SpringRabbitListener {

    @RabbitListener(queues = "simple.queue")
    public void listenSimpleQueueMessage(String msg) {
        System.out.println("消费者接收到消息：【" + msg + "】");
    }
}
```

两点说明：接收方法的参数类型需与发送的消息类型一致；监听器所在类必须交由 Spring 管理。

### 8.4 Work Queue

任务模型：多个消费者绑定同一个队列，共同消费，提高处理速度，同一条消息只会被其中一个消费者处理。

RabbitMQ 默认采用**轮询投递**，不判断消费者是否已处理完成，而是平均分配。若消费者1 每秒处理 50 条、消费者2 每秒处理 5 条，整体速度仍受限于较慢的消费者。

设置预取上限可实现"能者多劳"：

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1   # 每次只取 1 条，处理完并确认后才拿下一条
```

### 8.5 交换机

生产环境中消息先发给交换机，再由交换机路由到队列，而非直接发送到队列。交换机有四种类型，常用前三种：

| 类型 | 路由规则 |
|---|---|
| **Fanout** | 广播，发给所有绑定的队列，不看 RoutingKey |
| **Direct** | 队列绑定的 BindingKey 和消息的 RoutingKey **完全一致**才路由 |
| **Topic** | 和 Direct 类似，但 BindingKey 支持通配符 |
| **Headers** | 按消息头匹配，用得少 |

Topic 的通配符：`#` 匹配一个或多个词，`*` 匹配恰好一个词，词之间用 `.` 分隔。比如 `item.#` 能匹配 `item.spu.insert`，`item.*` 只能匹配 `item.spu`。

**声明队列和交换机**

不建议在管理控制台手动创建：程序所需的队列和交换机需人工同步给运维，容易遗漏。推荐由程序在启动时检查并自动创建。

Bean 方式：

```java
@Configuration
public class DirectConfig {

    @Bean
    public DirectExchange directExchange() {
        return ExchangeBuilder.directExchange("hmall.direct").build();
    }

    @Bean
    public Queue directQueue1() {
        return new Queue("direct.queue1");
    }

    /** 一个队列可以绑定多个 BindingKey */
    @Bean
    public Binding bindingQueue1WithRed(Queue directQueue1, DirectExchange directExchange) {
        return BindingBuilder.bind(directQueue1).to(directExchange).with("red");
    }

    @Bean
    public Binding bindingQueue1WithBlue(Queue directQueue1, DirectExchange directExchange) {
        return BindingBuilder.bind(directQueue1).to(directExchange).with("blue");
    }
}
```

注解方式可将声明与监听合并：

```java
@RabbitListener(bindings = @QueueBinding(
        value = @Queue(name = "direct.queue1"),
        exchange = @Exchange(name = "hmall.direct", type = ExchangeTypes.DIRECT),
        key = {"red", "blue"}
))
public void listenDirectQueue1(String msg) {
    System.out.println("消费者1 接收到消息：【" + msg + "】");
}

@RabbitListener(bindings = @QueueBinding(
        value = @Queue(name = "topic.queue1"),
        exchange = @Exchange(name = "hmall.topic", type = ExchangeTypes.TOPIC),
        key = "china.#"
))
public void listenTopicQueue1(String msg) {
    System.out.println("消费者接收到 topic 消息：【" + msg + "】");
}
```

### 8.6 消息转换器

`convertAndSend` 默认使用 JDK 序列化，消息在控制台中显示为不可读的字节流，体积膨胀，且无法跨语言解析。改用 JSON 转换器，publisher 与 consumer 两端都需配置：

```java
@Bean
public MessageConverter messageConverter() {
    Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
    // 自动给每条消息生成 id，后面做幂等判断时会用到
    converter.setCreateMessageIds(true);
    return converter;
}
```

依赖需要 `jackson-databind`（Spring MVC 通常已间接引入）。配置完成后可直接发送对象，接收方使用相同类型接收即可。

## 九、消息可靠性

上述用法只保证消息能够发送出去。但在支付等业务中，一旦 MQ 通知失败，支付服务中支付流水显示支付成功，而交易服务中订单仍为未支付，就会出现数据不一致。因此需要保证：**消息至少被消费者处理 1 次**。

消息从发送到处理完成，每个环节都存在丢失的可能：

- **发送时丢失**：连接 MQ 失败 / 消息到达 MQ 后未找到 Exchange / 到达 Exchange 后未找到匹配的 Queue / MQ 内部处理消息时发生异常
- **在 MQ 中丢失**：消息存入队列后尚未消费，MQ 宕机
- **消费时丢失**：消息接收后尚未处理完成即宕机 / 处理过程中抛出异常

对应的解决方向有三条：确保生产者把消息发到 MQ、确保 MQ 不丢失消息、确保消费者一定处理消息。

### 9.1 生产者重试机制

网络抖动导致连接 MQ 超时时，SpringAMQP 提供了重试机制：

```yaml
spring:
  rabbitmq:
    connection-timeout: 1s        # 连接超时时间
    template:
      retry:
        enabled: true             # 开启超时重试
        initial-interval: 1000ms  # 失败后的初始等待时间
        multiplier: 1             # 等待时长倍数，下次等待 = initial-interval * multiplier
        max-attempts: 3           # 最大重试次数
```

停止 MQ 容器（`docker stop mq`）后发送消息，可观察到每隔约 2 秒（连接超时 1 秒 + 等待 1 秒）重试一次，共重试 3 次。

注意：该重试为**阻塞式**，重试期间当前线程被阻塞。对性能有要求的业务建议禁用该机制；如确需使用，应合理配置等待时长与重试次数，或将发送消息的代码放到异步线程中执行。

### 9.2 生产者确认机制

网络连接通常不会导致消息丢失，但在 MQ 内部处理异常、找不到 Exchange、找到 Exchange 却无法路由到队列等情况下，消息仍会丢失。

RabbitMQ 提供了两种回执机制：

- **Publisher Confirm**：ack / nack，表示投递成功还是失败
- **Publisher Return**：路由失败时返回详细信息

开启之后，MQ 会根据消息的处理情况返回不同的回执：

| 情况 | 回执 |
|---|---|
| 消息投递到 MQ，但**路由失败** | 触发 Publisher Return 返回异常信息，**同时返回 ack** |
| 临时消息投递到 MQ，入队成功 | ack |
| 持久消息投递到 MQ，**入队并完成持久化** | ack |
| 其它情况 | nack |

注意第一行：路由失败返回的也是 ack（投递这件事成功了，只是没送进队列），错误信息走 return 回调。

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated   # 开启 confirm，异步回调方式
    publisher-returns: true              # 开启 return
```

`publisher-confirm-type` 有三种：`none`（关闭，默认）、`simple`（同步阻塞等回执）、`correlated`（异步回调，推荐）。

`ReturnCallback` 一个 `RabbitTemplate` 只能配一个，写在配置类里：

```java
@Slf4j
@Configuration
@RequiredArgsConstructor
public class MqConfig {

    private final RabbitTemplate rabbitTemplate;

    @PostConstruct
    public void init() {
        rabbitTemplate.setReturnsCallback(returned -> {
            log.error("消息路由失败，exchange={}, routingKey={}, replyCode={}, replyText={}, message={}",
                    returned.getExchange(),
                    returned.getRoutingKey(),
                    returned.getReplyCode(),
                    returned.getReplyText(),
                    returned.getMessage());
        });
    }
}
```

`ConfirmCallback` 不同：每条消息发送后的处理逻辑可能不同，因此它在**发送消息时指定**。做法是传入一个 `CorrelationData`，其内部持有一个 `Future`，提前为其添加回调：

```java
@Test
public void testConfirmCallback() throws InterruptedException {
    // 1. 创建 CorrelationData
    CorrelationData correlationData = new CorrelationData();
    // 2. 给里面的 Future 加回调
    correlationData.getFuture().addCallback(new ListenableFutureCallback<CorrelationData.Confirm>() {
        @Override
        public void onFailure(Throwable ex) {
            // Future 自身异常时才会走这里，基本不会发生
            log.error("发送消息失败", ex);
        }

        @Override
        public void onSuccess(CorrelationData.Confirm result) {
            if (result.isAck()) {
                log.debug("发送消息成功，收到 ack");
            } else {
                log.error("发送消息失败，收到 nack，原因：{}", result.getReason());
                // 这里做补偿：重发或者记录到数据库
            }
        }
    });

    // 3. 发送消息，故意用不存在的 routingKey
    rabbitTemplate.convertAndSend("hmall.direct", "xxx", "hello", correlationData);
    Thread.sleep(3000);
}
```

`CorrelationData` 里核心是两个东西：`id`（消息唯一标识，MQ 靠它区分不同消息的回执）和 `SettableListenableFuture`（回执结果就通过这个 Future 返回）。

三种测试结果：

- routingKey 错误 → 触发 return 回调，同时收到 ack
- routingKey 正确 → 不触发 return，仅收到 ack
- 交换机名称错误 → 仅收到 nack

> 开启确认机制会消耗 MQ 性能，一般不建议开启。触发确认的几种情况中：路由失败与交换机名称错误多由编码错误导致，MQ 内部故障概率较低。只有对可靠性要求极高的业务才需要开启，且通常只需处理 nack。

### 9.3 数据持久化

出于性能考虑，MQ 默认将数据存放于内存中作为临时数据，重启后丢失。为保证可靠性，需配置**交换机、队列、消息**三者持久化。

**交换机**：控制台添加时 `Durability` 选 `Durable` 就是持久化，`Transient` 是临时。SpringAMQP 用 Bean 或注解声明出来的，默认都是持久化的。

**队列**：同样有 `Durability` 参数，`QueueBuilder.durable("xxx")` 就是持久化队列。

**消息**：消息默认为临时的，这一点容易被忽略。在控制台发送时需将 `Delivery mode` 改为 `2 - Persistent`，代码中按如下方式发送：

```java
@Test
public void testPersistentMessage() {
    Message message = MessageBuilder
            .withBody("hello".getBytes(StandardCharsets.UTF_8))
            .setDeliveryMode(MessageDeliveryMode.PERSISTENT)
            .build();
    rabbitTemplate.convertAndSend("simple.queue", message);
}
```

两点说明：

1. 持久化仅保证未被消费的消息在重启后仍存在，消费完成后依然会被删除。
2. 开启生产者确认时，MQ 会在**消息持久化完成之后**才返回 ACK。出于性能考虑，消息并非逐条刷盘，而是约每 100 毫秒批量刷盘一次，因此 ACK 存在延迟，这也是 confirm 必须采用异步方式的原因。

### 9.4 LazyQueue

消息堆积通常由以下原因导致：消费者宕机或网络故障、消息发送量激增超过消费速度、消费者处理业务时发生阻塞。

消息堆积后内存占用持续升高，达到内存预警上限时，RabbitMQ 会将内存中的消息刷到磁盘，该行为称为 **PageOut**。PageOut 耗时较长且**会阻塞队列进程**，期间 MQ 不再处理任何新消息，生产者请求全部被阻塞。向队列发送 100 万条临时消息即可在控制台复现该现象。

Lazy Queue 用于解决该问题，其特征如下：

- 3.6.0 版本引入，收到消息后**直接写磁盘**而不是先放内存
- 消费者要消费时才从磁盘读进内存（懒加载）
- 支持数百万条消息存储
- **3.12 版本之后，LazyQueue 已经是所有队列的默认格式**，所以要么升级 3.12，要么把所有队列都设成 lazy

设置方式：控制台添加队列时指定参数 `x-queue-mode=lazy`，代码中也可声明：

```java
// Bean 方式
@Bean
public Queue lazyQueue() {
    return QueueBuilder.durable("lazy.queue")
            .lazy()   // 内部就是设置 x-queue-mode=lazy
            .build();
}

// 注解方式
@RabbitListener(queuesToDeclare = @Queue(
        name = "lazy.queue",
        durable = "true",
        arguments = @Argument(name = "x-queue-mode", value = "lazy")
))
public void listenLazyQueue(String message) {
    System.out.println("lazyQueue: " + message);
}
```

### 9.5 消费者确认机制

消费者处理完消息后，需向 MQ 返回回执，MQ 据此决定是否删除消息。回执有三种：

- **ack**：处理成功，从队列删除
- **nack**：处理失败，MQ 需要重新投递
- **reject**：处理失败并拒绝，从队列删除

`reject` 一般用于消息本身存在问题的场景（如格式错误，属于开发问题）。多数情况下在消费代码中 try catch，成功返回 ack，失败返回 nack。

SpringAMQP 已封装该逻辑，通过配置选择模式：

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto    # none / manual / auto
```

- `none`：消息投递后立即 ack 并删除，可靠性差，不建议使用
- `manual`：自行调用 `channel.basicAck()` / `basicNack()`，存在业务侵入但更灵活
- `auto`：SpringAMQP 通过 AOP 对消费逻辑做环绕增强：
  - 业务正常执行 → 返回 ack
  - 抛出**业务异常** → 返回 nack（重新投递）
  - 抛出**消息处理或校验异常**（`MessageConversionException`、`MethodArgumentNotValidException`、`MethodArgumentTypeMismatchException` 等）→ 返回 **reject**（直接丢弃）

该设计的合理性在于：消息转换或参数校验失败属于不可恢复错误，重新投递仍会失败，因此直接拒绝而非反复重试。

`manual` 模式下的写法：

```java
@RabbitListener(queues = "simple.queue")
public void listenSimpleQueue(Message message, Channel channel) throws IOException {
    try {
        // 业务处理
        channel.basicAck(message.getMessageProperties().getDeliveryTag(), false);
    } catch (Exception e) {
        // requeue=true 重新入队，false 则丢弃（或进死信交换机）
        channel.basicNack(message.getMessageProperties().getDeliveryTag(), false, true);
    }
}
```

### 9.6 失败重试机制

`auto` 模式下，消费者抛出业务异常会返回 nack，消息重新入队、再次投递、再次抛出异常。若消费者始终无法处理成功，就会形成无限循环，导致 MQ 压力持续升高。

Spring 提供了**本地重试**机制：消费者出现异常时在消费端本地重试，而不是无限制地将消息 requeue 回 MQ。

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        retry:
          enabled: true
          max-attempts: 3         # 最大重试次数
          initial-interval: 1000  # 重试间隔，单位毫秒
          multiplier: 1           # 间隔倍数，下次间隔 = initial-interval * multiplier
          stateless: true         # 无状态；如果业务里包含事务要改成 false
```

重试次数耗尽后会抛出 `AmqpRejectAndDontRequeueException`，最终返回 reject，消息被丢弃。

### 9.7 失败处理策略

重试耗尽后直接丢弃，对可靠性要求较高的业务不适用。Spring 允许自定义该策略，由 `MessageRecoverer` 接口定义，有三个实现：

- `RejectAndDontRequeueRecoverer`：直接 reject 并丢弃消息，**默认策略**
- `ImmediateRequeueMessageRecoverer`：返回 nack，消息重新入队（仍会形成循环）
- `RepublishMessageRecoverer`：将失败消息投递到指定交换机，**推荐方案**

采用第三种，创建专门的交换机与队列存放异常消息，后续由人工集中处理：

```java
@Configuration
@ConditionalOnProperty(name = "spring.rabbitmq.listener.simple.retry.enabled", havingValue = "true")
public class ErrorMessageConfig {

    @Bean
    public DirectExchange errorDirectExchange() {
        return new DirectExchange("error.direct");
    }

    @Bean
    public Queue errorQueue() {
        return new Queue("error.queue", true);
    }

    @Bean
    public Binding errorBinding(Queue errorQueue, DirectExchange errorDirectExchange) {
        return BindingBuilder.bind(errorQueue).to(errorDirectExchange).with("error");
    }

    /** 重试次数耗尽后，把消息连带异常信息一起投递到 error.direct */
    @Bean
    public MessageRecoverer messageRecoverer(RabbitTemplate rabbitTemplate) {
        return new RepublishMessageRecoverer(rabbitTemplate, "error.direct", "error");
    }
}
```

`@ConditionalOnProperty` 表示该配置仅在开启重试时生效。转投的消息头中会携带异常堆栈信息，便于排查。

### 9.8 公共配置抽取

上述配置每个微服务都需编写一份，可抽取为公共自动配置（置于 hm-common 模块）：

```java
@Configuration
@ConditionalOnProperty(name = "spring.rabbitmq.listener.simple.retry.enabled", havingValue = "true")
public class MqConsumeErrorAutoConfiguration {

    @Value("${spring.application.name}")
    private String serviceName;

    @Bean
    public DirectExchange errorDirectExchange() {
        return new DirectExchange("error.direct");
    }

    /** 队列名带上微服务名，避免各服务相互抢占消息 */
    @Bean
    public Queue errorQueue() {
        return new Queue(serviceName + ".error.queue", true);
    }

    @Bean
    public Binding errorBinding(Queue errorQueue, DirectExchange errorDirectExchange) {
        return BindingBuilder.bind(errorQueue).to(errorDirectExchange).with(serviceName);
    }

    @Bean
    public MessageRecoverer messageRecoverer(RabbitTemplate rabbitTemplate) {
        return new RepublishMessageRecoverer(rabbitTemplate, "error.direct", serviceName);
    }
}
```

将该类注册到 `META-INF/spring.factories`，各服务引入 hm-common 后即可自动生效。MQ 相关的公共配置（如重试策略）可统一放在 Nacos 的 `shared-mq.yaml` 中共享。

### 9.9 业务幂等性

幂等源自数学概念 `f(x) = f(f(x))`（如绝对值函数）。在程序中指**同一业务执行一次与执行多次，对业务状态的影响一致**。

查询、按 id 删除天然幂等，更新操作通常不是。例如取消订单恢复库存，重复执行会导致库存重复增加；退款业务重复执行则会造成资金损失。

重复执行无法完全避免，常见来源包括：页面卡顿导致表单重复提交、服务间调用重试、MQ 消息重复投递。

以支付业务为例：用户支付成功后发送 MQ 消息通知交易服务将订单改为已支付。若因网络故障生产者未收到确认，消息随后被重新投递，而在此期间用户已申请退款、订单状态变为已退款，则迟到的消息会将订单重新改回已支付，导致业务异常。

两种方案：

**方案一：唯一消息 ID**

每条消息携带唯一 id，消费者处理成功后将 id 存入数据库，再次收到相同 id 时放弃处理。SpringAMQP 的 `MessageConverter` 自带该功能，开启即可：

```java
@Bean
public MessageConverter messageConverter() {
    Jackson2JsonMessageConverter converter = new Jackson2JsonMessageConverter();
    converter.setCreateMessageIds(true);   // 自动创建消息 id
    return converter;
}
```

缺点是需要改造数据库，且"记录 messageId"与"业务操作"必须置于同一事务中，否则仍可能重复处理。

**方案二：业务判断（推荐）**

基于业务自身状态进行判断，无需改动表结构。例如将订单改为已支付，前提是订单当前处于"未支付"状态：

```java
public void markOrderPaySuccess(Long orderId) {
    // update `order` set `status` = 2, `pay_time` = now() where `id` = ? and `status` = 1
    lambdaUpdate()
            .set(Order::getStatus, 2)
            .set(Order::getPayTime, LocalDateTime.now())
            .eq(Order::getId, orderId)
            .eq(Order::getStatus, 1)   // 关键：只有未支付的才更新
            .update();
}
```

将判断与更新合并为一条 SQL 是必要的：若先查询订单再调用 `updateById`，两步之间存在极小概率的线程安全问题。合并后条件不满足则 SQL 匹配不到数据，天然幂等。

> 前文秒杀方案中"乐观锁扣库存 `where stock > 0`"采用的是同一思路。

### 9.10 兜底方案

上述机制无法保证 100% 可靠。若 MQ 通知最终失败，可在被动接收通知之外**主动查询**。

具体做法：交易服务启动定时任务，每隔 20 秒向支付服务查询一次支付状态，若发现订单已支付则更新订单状态。这样即使 MQ 通知完全失败，仍可通过定时任务保证订单状态的最终一致性。

注意：查询时机无法精确确定（查询时用户可能正在支付过程中），因此只能采用定期轮询的方式。

## 十、延迟消息

**延迟消息**：生产者发送消息时指定一个时间，消费者不会立即收到，而是在指定时间之后才收到。

典型场景是电商的超时订单：下单时立即扣减库存（类似电影院选座），若用户一直不付款则会一直占用库存，因此超过 30 分钟未支付需自动取消订单并释放库存。

RabbitMQ 中有两种实现方式。

### 10.1 死信交换机 + TTL

队列中的消息满足以下任一条件时成为**死信**：

1. 消费者 `basic.reject` 或 `basic.nack` 声明消费失败，并且 `requeue` 设为 false
2. 消息过期了，超时无人消费
3. 队列满了，消息塞不进去

若该队列通过 `dead-letter-exchange` 属性指定了另一个交换机，死信会被投递到该交换机，称为**死信交换机（DLX）**，与 DLX 绑定的队列即可接收这些死信。

基于该机制实现延迟消息：让消息进入一个**没有消费者监听的队列**并设置 TTL，消息过期后成为死信，自动转发到死信交换机，最终投递到真正被消费的队列。

```java
/** 没人监听的 TTL 队列：消息 10 秒过期后转投到死信交换机 */
@Bean
public Queue ttlQueue() {
    return QueueBuilder.durable("ttl.queue")
            .deadLetterExchange("hmall.direct")   // x-dead-letter-exchange
            .deadLetterRoutingKey("blue")         // x-dead-letter-routing-key
            .ttl(10000)                           // x-message-ttl，队列级，所有消息统一 10 秒
            .build();
}
```

也可按消息单独设置过期时间，相比队列级 TTL 更灵活：

```java
@Test
public void testSendExpiredMessage() {
    rabbitTemplate.convertAndSend("simple.direct", "", "hello delay message.", message -> {
        message.getMessageProperties().setExpiration("10000");   // 10 秒后过期
        return message;
    });
}
```

两点注意事项：

- 消息成为死信投递到 DLX 时会**沿用原有的 RoutingKey**，因此 DLX 需使用 direct 类型才能路由到指定队列
- **TTL 存在偏差**：RabbitMQ 的过期判定是"追溯式"的，消息 TTL 到期后不一定立即被处理，需等其到达队首时才被处理。队列中消息堆积较多时，设置的 5 秒延迟可能几十秒后才生效

### 10.2 延迟消息插件

基于死信的实现方式较为繁琐，RabbitMQ 社区提供了专门的延迟消息插件。

**安装**（基于 Docker）：

```bash
# 1. 查看插件目录的挂载位置
docker volume inspect mq-plugins

# 2. 将插件上传到 Mountpoint 对应的目录
#    插件：rabbitmq_delayed_message_exchange-3.8.17.8f537ac.ez（MQ 为 3.8 则下载 3.8.17 版本）

# 3. 进入容器启用插件
docker exec -it mq rabbitmq-plugins enable rabbitmq_delayed_message_exchange

# 4. 重启容器
docker restart mq
```

**声明延迟交换机**：

```java
// 注解方式
@RabbitListener(bindings = @QueueBinding(
        value = @Queue(value = "delay.queue", durable = "true"),
        exchange = @Exchange(value = "delay.direct", delayed = "true"),
        key = "delay"
))
public void listenDelayQueueMessage(String message) {
    System.out.println("收到延迟消息：" + message + " " + LocalTime.now());
}

// Bean 方式
@Bean
public DirectExchange delayDirectExchange() {
    return ExchangeBuilder.directExchange("delay.direct")
            .delayed()      // 关键：延迟交换机
            .durable(true)
            .build();
}
```

**发送延迟消息**：

```java
@Test
public void testDelayMessage() {
    System.out.println("发送时间：" + LocalTime.now());
    rabbitTemplate.convertAndSend("delay.direct", "delay", "hello, delay message", message -> {
        message.getMessageProperties().setDelay(5000);   // 延迟 5 秒
        return message;
    });
}
```

> 插件内部会维护一张本地数据库表，配合 Erlang Timers 实现计时。延迟时间设得过长，堆积的延迟消息会很多，CPU 开销大，时间还容易有误差，所以不建议设太长的延迟。

### 10.3 多级延迟消息处理超时订单

下单后直接发送一条延迟 30 分钟的消息虽然可行，但存在两个问题：消息需在 MQ 中滞留 30 分钟，占用资源；且大多数用户会在 1 分钟内完成支付。

优化做法是**分多次检测**：在下单后的第 10 秒、20 秒、30 秒、45 秒、60 秒、1 分 30 秒、2 分……30 分各发送一条延迟消息。每次收到消息先查询订单状态，若已支付则不再发送下一级，只有确认超时才取消订单。

先定义通用消息体（置于 hm-common 模块）：

```java
@Data
@NoArgsConstructor
public class MultiDelayMessage<T> {

    /** 消息内容 */
    private T data;
    /** 记录后续延迟时间的集合 */
    private List<Integer> delayMillis;

    public MultiDelayMessage(T data, List<Integer> delayMillis) {
        this.data = data;
        this.delayMillis = delayMillis;
    }

    public static <T> MultiDelayMessage<T> of(T data, Integer... delayMillis) {
        return new MultiDelayMessage<>(data, CollUtils.newArrayList(delayMillis));
    }

    /** 取出并移除下一个延迟时间 */
    public Integer removeNextDelay() {
        return this.delayMillis.remove(0);
    }

    /** 是否还有下一个延迟时间 */
    public boolean hasNextDelay() {
        return !delayMillis.isEmpty();
    }
}
```

MQ 相关常量单独抽取：

```java
public interface TradeMqConstants {
    String DELAY_EXCHANGE = "trade.delay.topic";
    String DELAY_ORDER_QUEUE = "trade.order.delay.queue";
    String DELAY_ORDER_ROUTING_KEY = "order.query";
}
```

下单业务中发送第一条延迟消息：

```java
// 下单完成后，发送多级延迟消息，检查支付状态
MultiDelayMessage<Long> msg = MultiDelayMessage.of(orderId, 10000, 10000, 10000, 15000,
        15000, 30000, 30000, 30000, 60000, 60000, 60000, 60000, 600000, 600000, 600000);
rabbitTemplate.convertAndSend(
        TradeMqConstants.DELAY_EXCHANGE,
        TradeMqConstants.DELAY_ORDER_ROUTING_KEY,
        msg,
        message -> {
            message.getMessageProperties().setDelay(msg.removeNextDelay());
            return message;
        });
```

监听器同时负责发送下一级延迟消息：

```java
@Component
@RequiredArgsConstructor
public class OrderStatusListener {

    private final IOrderService orderService;
    private final PayClient payClient;
    private final RabbitTemplate rabbitTemplate;

    @RabbitListener(bindings = @QueueBinding(
            value = @Queue(value = TradeMqConstants.DELAY_ORDER_QUEUE, durable = "true"),
            exchange = @Exchange(value = TradeMqConstants.DELAY_EXCHANGE, delayed = "true",
                    type = ExchangeTypes.TOPIC, durable = "true"),
            key = TradeMqConstants.DELAY_ORDER_ROUTING_KEY
    ))
    public void listenOrderCheckDelayMessage(MultiDelayMessage<Long> message) {
        // 1. 取订单 id
        Long orderId = message.getData();

        // 2. 订单不存在或已支付，放弃处理
        Order order = orderService.getById(orderId);
        if (order == null || order.getStatus() > 1) {
            return;
        }

        // 3. 查支付单，已支付则更新订单状态
        PayOrderDTO payOrderDTO = payClient.queryPayOrderByBizOrderNo(orderId);
        if (payOrderDTO != null && payOrderDTO.getStatus() == 3) {
            orderService.markOrderPaySuccess(orderId);
            return;
        }

        // 4. 还没支付，还有下一级就继续发
        if (message.hasNextDelay()) {
            Integer delayTime = message.removeNextDelay();
            rabbitTemplate.convertAndSend(
                    TradeMqConstants.DELAY_EXCHANGE,
                    TradeMqConstants.DELAY_ORDER_ROUTING_KEY,
                    message,
                    msg -> {
                        msg.getMessageProperties().setDelay(delayTime);
                        return msg;
                    });
            return;
        }

        // 5. 延迟时间用完了还没支付，取消订单
        orderService.cancelOrder(orderId);
    }
}
```

取消订单包含两个操作：将订单状态改为已关闭（值为 5）、恢复订单中已扣减的商品库存。

```java
@Override
@GlobalTransactional
public void cancelOrder(Long orderId) {
    // 1. 订单状态改为已关闭（带 status=1 条件，保证幂等）
    lambdaUpdate()
            .set(Order::getStatus, 5)
            .set(Order::getCloseTime, LocalDateTime.now())
            .eq(Order::getId, orderId)
            .eq(Order::getStatus, 1)
            .update();

    // 2. 恢复库存：订单详情里的购买数量取负数，再调商品服务扣减
    List<OrderDetail> details = detailService.list(
            new LambdaQueryWrapper<OrderDetail>().eq(OrderDetail::getOrderId, orderId));
    if (CollUtils.isEmpty(details)) {
        return;
    }
    List<OrderDetailDTO> dtos = BeanUtils.copyList(details, OrderDetailDTO.class);
    for (OrderDetailDTO dto : dtos) {
        dto.setNum(-dto.getNum());
    }
    itemClient.deductStock(dtos);
}
```

### 10.4 两种方案对比

| | 死信 + TTL | 延迟消息插件 |
|---|---|---|
| 优点 | 原生支持，无需安装插件 | 用法简单，延迟准确，不受队头阻塞影响 |
| 缺点 | 需借助死信机制中转，TTL 存在偏差 | 需安装插件，延迟时间过长会增加 CPU 开销 |

两种方案均不适用于延迟时间过长的场景（数小时或数天），此类需求建议使用定时任务扫描数据库实现。
