# 乐观锁

## 核心思想

乐观锁对并发冲突持乐观态度：默认认为多数情况下不会发生数据冲突，因此操作前不加锁，直接执行读写操作；只有在最终提交更新时，才校验数据是否被其他操作修改过。如果检测到冲突，则返回失败，由业务层决定重试或放弃。

> **注意**：乐观锁本质不是 "锁"，而是一种无锁的并发控制方案。

## 常见实现

### 版本号机制（数据库最常用）

在数据表中增加一个 `version` 字段，记录数据的版本号。每次更新数据时，必须校验当前版本号与读取时的版本号是否一致，一致才允许更新，并将版本号 + 1。

#### SQL 示例

```sql
-- 读取数据时拿到 version = 1
UPDATE goods 
SET stock = stock - 1, version = version + 1 
WHERE id = 1001 AND version = 1;
```

通过判断受影响行数是否为 0，即可知道是否更新成功。如果为 0，说明在读取数据到提交更新期间，其他事务已经修改过该数据，当前更新发生冲突。

#### Java 实现示例

```java
@Service
public class StockService {

    @Autowired
    private StockMapper stockMapper;

    public boolean deductStock(Long goodsId) {
        // 1. 查询商品库存及版本号
        Stock stock = stockMapper.selectById(goodsId);

        // 2. 执行扣减：版本号作为条件，扣减成功后版本号 + 1
        int affectedRows = stockMapper.deductStock(goodsId, stock.getVersion());

        // 3. 通过受影响行数判断是否更新成功
        return affectedRows > 0;
    }
}
```

```java
// Mapper 接口
@Update("UPDATE stock SET count = count - 1, version = version + 1 " +
        "WHERE goods_id = #{goodsId} AND version = #{version} AND count > 0")
int deductStock(@Param("goodsId") Long goodsId, @Param("version") Integer version);
```

### CAS 算法（编程层面最常用）

全称 **Compare-And-Swap（比较并交换）**，是 CPU 级别的原子指令。它在更新值时，先比较当前值是否等于预期的旧值，相等才用新值覆盖，否则不操作。

Java 中的 `AtomicInteger`、`AtomicLong` 等原子类，就是基于 CAS 实现的乐观锁。

```java
public class CASDemo {

    public static void main(String[] args) {
        AtomicInteger count = new AtomicInteger(0);

        // 自增操作底层使用 CAS
        count.incrementAndGet();

        //  compareAndSet(oldValue, newValue)
        boolean success = count.compareAndSet(1, 10);
        System.out.println("CAS 是否成功：" + success);
        System.out.println("当前值：" + count.get());
    }
}
```

## 执行流程

1. 读取共享数据的当前状态（同时记录版本号 / 旧值）
2. 基于读取的数据执行业务计算
3. 提交更新时，校验数据是否被修改
4. 校验通过则更新成功，校验失败则重试 / 回滚

## ABA 问题

### 什么是 ABA 问题

假设线程 A 读取变量值为 A，准备将其改为 B。在这期间，线程 B 将变量从 A 改为 B，又改回 A。当线程 A 执行 CAS 操作时，发现变量值仍然是 A，于是认为没有变化，成功更新为 B。但实际上变量已经被修改过，这就是 ABA 问题。

### 解决方案

使用 **版本号（Version）** 或 **时间戳（Timestamp）** 来标识数据的修改次数，CAS 时不仅比较值，还比较版本号是否一致。

```java
// AtomicStampedReference 通过版本号解决 ABA 问题
AtomicStampedReference<Integer> value = new AtomicStampedReference<>(100, 0);

int[] stampHolder = new int[1];
Integer oldValue = value.get(stampHolder);
int oldStamp = stampHolder[0];

// 更新时同时比较值和版本号
value.compareAndSet(oldValue, 200, oldStamp, oldStamp + 1);
```

## 适用场景

- 读多写少的业务场景
- 冲突概率低的场景
- 对响应速度要求高的场景
- 例如：商品浏览量更新、用户信息修改、库存查询

# 乐观锁与悲观锁对比

| 对比维度 | 悲观锁 | 乐观锁 |
|:---|:---|:---|
| 核心假设 | 并发冲突一定会发生 | 并发冲突很少发生 |
| 加锁方式 | 操作前加锁，独占资源 | 操作前不加锁，提交时校验 |
| 冲突处理 | 冲突时阻塞等待 | 冲突时重试 / 失败回滚 |
| 性能开销 | 加锁解锁开销大，阻塞耗时 | 无锁开销，但冲突重试有消耗 |
| 数据一致性 | 强一致性，隔离性好 | 最终一致性，依赖重试机制 |
| 典型问题 | 死锁、锁饥饿、长事务锁占用 | ABA 问题、高冲突下重试风暴 |
| 典型实现 | `SELECT ... FOR UPDATE`、`synchronized` | 版本号机制、CAS 原子类 |

## 实际作用总结

两者最终都是为了保证并发环境下共享数据的正确性，但适用场景互补：

- **悲观锁**：优先保证数据安全，牺牲部分性能，适合对数据一致性要求极高、写操作密集的业务
- **乐观锁**：优先保证系统性能，在低冲突场景下大幅提升并发吞吐量，适合读多写少、对响应速度要求高的业务
