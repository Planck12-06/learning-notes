# 缓存技术

由于网络带宽和服务器硬件成本的限制，在高并发场景下服务器的性能会受到影响。为了解决这个问题，就需要使用缓存技术。

缓存需要将热点数据提前加载到缓存中，当下一个请求过来时，可以直接从缓存中获取，而不需要从数据库中查询。缓存技术可以提高服务器的性能，减少数据库的压力。

## 缓存架构

```
请求 → [缓存层] → 命中 → 直接返回
              ↓ 未命中
         [数据库] → 查询数据 → 写入缓存 → 返回数据
```

# RedisTemplate 缓存实现

通过 `RedisTemplate` 的方式手动操作 Redis 实现缓存功能。

## 核心依赖

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

## 配置项

| 配置项 | 说明 |
|:---|:---|
| `spring.data.redis.host` | Redis 服务器地址 |
| `spring.data.redis.port` | Redis 端口（默认 6379） |
| `spring.data.redis.password` | Redis 密码 |
| `spring.data.redis.database` | 数据库索引（默认 0） |

## 使用示例

```java
@Service
public class DeptServiceImpl implements DeptService {

    @Autowired
    private DeptMapper deptMapper;

    @Autowired
    private StringRedisTemplate stringRedisTemplate;

    private static final String DEPT_CACHE_KEY = "dept:";

    @Override
    public Result list() {
        // 1. 先查询缓存
        String cacheData = stringRedisTemplate.opsForValue().get(DEPT_CACHE_KEY + "list");

        // 2. 缓存命中，直接返回
        if (StringUtils.hasText(cacheData)) {
            List<Dept> deptList = JSON.parseArray(cacheData, Dept.class);
            return Result.success(deptList);
        }

        // 3. 缓存未命中，查询数据库
        List<Dept> deptList = deptMapper.list();

        // 4. 将数据写入缓存，设置过期时间
        stringRedisTemplate.opsForValue()
                .set(DEPT_CACHE_KEY + "list", JSON.toJSONString(deptList), 30, TimeUnit.MINUTES);

        return Result.success(deptList);
    }
}
```

## 执行流程

1. **查询缓存**：先从 Redis 中获取数据
2. **缓存命中**：如果存在且有效，直接返回缓存数据
3. **缓存未命中**：查询数据库获取原始数据
4. **写入缓存**：将查询结果写入 Redis，设置合理的过期时间
5. **返回结果**：将数据返回给客户端

# Spring Cache 注解式缓存

Spring 提供了基于注解的缓存抽象，可以更方便地管理缓存操作。

## 开启缓存

在 Spring Boot 启动类上添加 `@EnableCaching` 注解：

```java
@EnableCaching
@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

## 常用注解

<table>
<thead>
<tr>
<th>注解</th>
<th>说明</th>
</tr>
</thead>
tbody>
<tr><td><code>@Cacheable</code></td><td>在方法执行前先查看缓存，有则返回，没有则执行方法并将结果存入缓存</td></tr>
<tr><td><code>@CachePut</code></td><td>将方法的返回值放入缓存中（每次都会执行方法）</td></tr>
<tr><td><code>@CacheEvict</code></td><td>删除一条或多条缓存数据</td></tr>
<tr><td><code>@Caching</code></td><td>组合多个缓存注解</td></tr>
</tbody>
</table>

## 使用示例

```java
@Service
public class EmpServiceImpl implements EmpService {

    @Autowired
    private EmpMapper empMapper;

    // 查询时使用缓存
    @Cacheable(value = "emp", key = "#id")
    public Emp getById(Integer id) {
        return empMapper.getById(id);
    }

    // 更新时更新缓存
    @CachePut(value = "emp", key = "#emp.id")
    public Emp update(Emp emp) {
        emp.setUpdateTime(LocalDateTime.now());
        empMapper.update(emp);
        return emp;
    }

    // 删除时清除缓存
    @CacheEvict(value = "emp", key = "#id")
    public void delete(Integer id) {
        empMapper.delete(id);
    }

    // 批量删除时清空整个缓存分区
    @CacheEvict(value = "emp", allEntries = true)
    public void deleteBatch(List<Integer> ids) {
        empMapper.deleteBatch(ids);
    }
}
```

# 缓存常见问题

## 缓存穿透

### 产生原因

用户请求的数据在缓存中和数据库中都不存在，不断发起这样的请求，给数据库带来巨大压力。

### 解决方案

- **缓存 null 值**：将空结果也缓存，设置较短过期时间
- **布隆过滤**：快速判断数据是否可能存在
- **增强 id 的复杂度**：避免被猜测 id 规律
- **做好数据的基础格式校验**：在入口处拦截非法请求
- **加强用户权限校验**：防止恶意攻击
- **做好热点参数的限流**：保护数据库不被压垮

### 缓存空值示例

```java
/**
 * 缓存穿透方案：缓存空值
 * <p>思路：缓存未命中时查询数据库；若数据库也不存在，则缓存一个空值（短 TTL），后续相同请求直接返回空值，避免反复查询数据库。</p>
 * <p>优点：实现简单，效果直接。</p>
 * <p>缺点：额外占用缓存空间，可能造成短期数据不一致。</p>
 */
public <R, ID> R queryWithPassThrough(String keyPrefix, ID id, Class<R> type,
                                      Function<ID, R> dbFallback,
                                      Long time, TimeUnit unit) {
    String key = keyPrefix + id;

    // 1. 从 Redis 查询缓存
    String json = stringRedisTemplate.opsForValue().get(key);

    // 2. 命中有效缓存，直接返回
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, type);
    }

    // 3. 命中空缓存（之前缓存过空串），直接返回 null，防止穿透
    if (json != null) {
        return null;
    }

    // 4. 缓存未命中，查询数据库
    R r = dbFallback.apply(id);

    // 5. 数据库不存在：写入空缓存（短 TTL），防止缓存穿透
    if (r == null) {
        stringRedisTemplate.opsForValue()
                .set(key, "", RedisConstants.CACHE_NULL_TTL, TimeUnit.MINUTES);
        return null;
    }

    // 6. 数据库存在：写入缓存并设置 TTL
    this.set(key, r, time, unit);
    return r;
}
```

## 缓存击穿

### 产生原因

某个热点 Key 过期瞬间，大量并发请求同时打到数据库。

### 解决方案

- **互斥锁**：只允许一个线程重建缓存
- **逻辑过期**：不设置真正的过期时间，由业务逻辑判断

### 互斥锁示例

```java
/**
 * 缓存击穿方案：互斥锁
 * <p>思路：缓存未命中时，先抢分布式锁。抢到锁的线程查数据库并重建缓存；没抢到锁的线程自旋等待、递归重试，直到拿到重建后的缓存。</p>
 * <p>优点：数据强一致，数据库只会被串行查询一次。</p>
 * <p>缺点：高并发下未抢到锁的请求会被阻塞等待，存在一定的锁等待开销。</p>
 */
public <R, ID> R queryWithMutex(String keyPrefix, ID id, Class<R> type,
                                Function<ID, R> dbFallback,
                                Long time, TimeUnit unit) {
    String key = keyPrefix + id;

    // 1. 从 Redis 查询缓存
    String json = stringRedisTemplate.opsForValue().get(key);

    // 2. 命中有效缓存，直接返回
    if (StrUtil.isNotBlank(json)) {
        return JSONUtil.toBean(json, type);
    }

    // 3. 命中空缓存，直接返回 null，防止穿透
    if (json != null) {
        return null;
    }

    // 4. 缓存未命中，开始缓存重建
    String lockKey = RedisConstants.LOCK_SHOP_KEY + id;
    R r = null;

    try {
        // 4.1 尝试获取互斥锁（SETNX）
        boolean isLock = tryLock(lockKey);

        if (!isLock) {
            // 4.2 获取锁失败，其他线程正在重建缓存，休眠片刻后递归重试
            Thread.sleep(100);
            return queryWithMutex(keyPrefix, id, type, dbFallback, time, unit);
        }

        // 4.3 获取锁成功，查询数据库
        r = dbFallback.apply(id);

        // 4.4 数据库不存在：写入空缓存（短 TTL），防止缓存穿透
        if (r == null) {
            stringRedisTemplate.opsForValue()
                    .set(key, "", time, unit);
            return null;
        }

        // 4.5 数据库存在：写入缓存并设置 TTL
        stringRedisTemplate.opsForValue()
                .set(key, JSONUtil.toJsonStr(r), time, unit);

    } catch (InterruptedException e) {
        throw new RuntimeException(e);
    } finally {
        // 5. 无论成功失败，释放互斥锁
        unLock(lockKey);
    }

    return r;
}

/**
 * 尝试获取互斥锁：利用 Redis 的 SETNX（setIfAbsent），只有 key 不存在时才能设置成功
 */
private boolean tryLock(String key) {
    Boolean flag = stringRedisTemplate.opsForValue()
            .setIfAbsent(key, "1", RedisConstants.CACHE_SHOP_TTL, TimeUnit.MINUTES);
    return BooleanUtil.isTrue(flag);
}

/**
 * 释放互斥锁：直接删除锁的 key
 */
private void unLock(String key) {
    stringRedisTemplate.delete(key);
}
```

### 逻辑过期示例

```java
/**
 * 缓存击穿方案：逻辑过期
 * <p>思路：缓存不设置真正的过期时间，而是在缓存数据中保存一个逻辑过期时间。当发现数据逻辑过期后，获取互斥锁并开启独立线程异步重建缓存，当前请求继续返回旧数据。</p>
 * <p>优点：高可用，不会阻塞用户请求。</p>
 * <p>缺点：会返回短期旧数据，牺牲一定的一致性。</p>
 */
public <R, ID> R queryWithLogicExpire(String keyPrefix, ID id, Class<R> type,
                                      Function<ID, R> dbFallback,
                                      Long time, TimeUnit unit) {
    String key = keyPrefix + id;

    // 1. 从 Redis 查询缓存
    String json = stringRedisTemplate.opsForValue().get(key);

    // 2. 未命中（逻辑过期方案默认已预热），返回 null
    if (StrUtil.isBlank(json)) {
        return null;
    }

    // 3. 命中，把 json 反序列化为 RedisData（内含数据 + 逻辑过期时间）
    RedisData redisData = JSONUtil.toBean(json, RedisData.class);
    R r = JSONUtil.toBean((JSONObject) redisData.getData(), type);
    LocalDateTime expireTime = redisData.getExpireTime();

    // 4. 判断缓存是否逻辑过期
    if (expireTime.isAfter(LocalDateTime.now())) {
        // 5. 未过期，直接返回数据
        return r;
    }

    // 6. 已过期，尝试获取互斥锁，准备异步重建缓存
    String lockKey = RedisConstants.LOCK_SHOP_KEY + id;
    boolean isLock = tryLock(lockKey);

    if (isLock) {
        // 7. 获取锁成功，开启独立线程异步重建缓存（不阻塞当前用户请求）
        CACHE_REBUILD_EXECUTOR.submit(() -> {
            try {
                // 7.1 查询数据库并重建缓存
                R r1 = dbFallback.apply(id);
                this.setWithLogicalExpire(key, r1, time, unit);
            } catch (Exception e) {
                throw new RuntimeException(e);
            } finally {
                // 7.2 释放互斥锁
                unLock(lockKey);
            }
        });
    }

    // 8. 返回逻辑过期的旧数据（兜底，保证用户体验）
    return r;
}
```

## 缓存雪崩

### 产生原因

同一时段大量的缓存 Key 同时过期或 Redis 服务宕机，导致所有请求打到数据库，带来巨大压力。

### 解决方案

- **随机过期时间**：避免大量 Key 同时过期
- **高可用集群**：Redis 主从 + 哨兵/集群
- **限流降级**：保护数据库不被压垮
- **多级缓存**：热点数据缓存到 Redis，其他数据缓存到本地缓存
