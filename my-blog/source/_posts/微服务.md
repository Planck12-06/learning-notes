# 微服务

> 本笔记基于黑马程序员 2024 SpringCloud 微服务课程，以「黑马商城 hmall」从单体项目改造为微服务的项目为主线，完整记录**服务拆分、注册发现、配置管理、远程调用、网关路由、服务保护、分布式事务**等全套技术栈的使用方式与原理。

微服务要解决的核心问题只有一个：**把"一个包搞定一切"的单体应用，拆成一组可以独立开发、独立部署、独立伸缩的服务后，如何让这些服务之间能互相找到、互相调用、互相不拖垮彼此。**

整条技术栈的演进顺序如下：

| 阶段 | 要解决的问题 | 对应组件 |
|---|---|---|
| 服务拆分 | 单体耦合严重，团队协作成本高 | 按业务模块拆分 + 独立数据库 |
| 远程调用 | 服务之间如何通信 | `RestTemplate` → OpenFeign |
| 注册发现 | 服务地址硬编码、实例上下线无感知 | Nacos Discovery |
| 负载均衡 | 多实例该选哪一个 | Spring Cloud LoadBalancer / NacosRule |
| 配置管理 | 配置分散、修改要重启 | Nacos Config（热更新、共享配置） |
| 统一入口 | 前端要记 N 个地址、鉴权逻辑重复 | Spring Cloud Gateway |
| 服务保护 | 雪崩、高并发打垮服务 | Sentinel |
| 分布式事务 | 跨服务、跨库的数据一致性 | Seata |
| 异步解耦 | 同步链路太长、性能差 | MQ（{% post_link 消息队列 消息队列 %}） |
| 部署运维 | 几十个服务怎么部署 | Docker（{% post_link 项目部署-Dockers 项目部署-Dockers %}） |

## 一、认识微服务

### (一) 单体架构

**单体架构**：将业务的所有功能集中在一个项目中开发，打成一个包部署。

优点：

- 架构简单
- 部署成本低（一台服务器、一个 jar 包搞定）

缺点：

- **团队协作成本高**：所有人改同一份代码，冲突不断
- **系统发布效率低**：任何一处修改都要全量重新打包、全量发布
- **系统可用性差**：一个模块出现 OOM、死循环，整个应用全部不可用

> 总结：单体架构适合功能相对简单、规模较小的项目。

### (二) 分布式架构与微服务架构

**分布式架构**：根据业务功能对系统进行拆分，每个业务模块作为独立项目开发，称为一个**服务**。

**微服务架构**：是"服务化"思想指导下的一套**最佳实践架构方案**。服务化，就是把单体架构中的功能模块拆分为多个独立项目。

微服务经过良好的架构设计后具备如下特征：

| 特征 | 说明 |
|---|---|
| **单一职责** | 一个服务只做一件事，拆分粒度更小 |
| **团队自治** | 每个团队负责自己的服务，技术选型、发布节奏独立 |
| **服务自治** | 独立部署、独立数据库、独立进程，互不干扰 |
| **面向服务** | 对外暴露统一标准的接口（RESTful / RPC） |
| **隔离性强** | 服务调用做好隔离、容错、降级，避免出现级联失败 |

### (三) SpringCloud

SpringCloud 集成了各种微服务功能组件，并基于 SpringBoot 实现了这些组件的**自动装配**，从而提供了良好的开箱即用体验。它主要覆盖以下能力：

- 服务注册发现
- 统一配置管理
- 服务远程调用
- 统一网关路由
- 服务链路监控
- 流控、降级、保护

SpringCloud 本身只是一个**规范集合**，国内最主流的落地实现是 **Spring Cloud Alibaba（SCA）**，组件对应关系如下：

| 能力 | Spring Cloud Netflix（老） | Spring Cloud Alibaba（新） |
|---|---|---|
| 注册中心 | Eureka | **Nacos Discovery** |
| 配置中心 | Spring Cloud Config | **Nacos Config** |
| 远程调用 | Feign | **OpenFeign** |
| 负载均衡 | Ribbon | **Spring Cloud LoadBalancer / NacosRule** |
| 服务网关 | Zuul | **Spring Cloud Gateway** |
| 服务保护 | Hystrix | **Sentinel** |
| 分布式事务 | — | **Seata** |
| 链路追踪 | Sleuth + Zipkin | SkyWalking / Micrometer Tracing |

### (四) 版本选型

SpringCloud 与 SpringBoot 存在**严格版本对应关系**，选错版本会导致各种莫名的启动报错。常用对应关系如下（具体以官方 Release Notes 为准）：

| Spring Cloud 版本 | 代号 | Spring Boot 版本 | JDK |
|---|---|---|---|
| 2023.0.x | Leyton | 3.2.x / 3.3.x | 17+ |
| 2022.0.x | Kilburn | 3.0.x / 3.1.x | 17+ |
| 2021.0.x | Jubilee | 2.6.x / 2.7.x | 8+ |
| 2020.0.x | Ilford | 2.4.x / 2.5.x | 8+ |
| Hoxton | — | 2.2.x / 2.3.x | 8 |

Spring Cloud Alibaba 又在 Spring Cloud 之上再做一层对应：

| Spring Cloud Alibaba | Spring Cloud | Spring Boot | Nacos |
|---|---|---|---|
| 2023.0.1.0 | 2023.0.x | 3.2.x | 2.3.x |
| 2022.0.0.0 | 2022.0.x | 3.0.x | 2.2.x |
| 2021.0.4.0 | 2021.0.x | 2.6.x / 2.7.x | 2.x |

在工程实践中，通常通过父工程的 `dependencyManagement` 统一管理版本，子模块只声明依赖不写版本号：

```xml

            <version>2023.0.1</version>
            <type>pom</type>
            <scope>import</scope>

        <!-- Spring Cloud Alibaba -->
        <dependency>
            <groupId>com.alibaba.cloud</groupId>
            <artifactId>spring-cloud-alibaba-dependencies</artifactId>
            <version>2023.0.1.0</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

## 二、微服务拆分与远程调用

### (一) 拆分原则

什么时候拆？

- **创业型项目**：先采用单体架构快速开发、快速试错，随着规模扩大再逐步拆分
- **确定的大型项目**：资金充足、目标明确、业务复杂，可以直接选择微服务架构，避免后续大规模重构

怎么拆？业界通用目标是做到：

- **高内聚**：每个服务的职责要尽量单一，包含的业务相互关联度高、完整度高
- **低耦合**：每个服务的功能要相对独立，尽量不要依赖其它服务

具体到落地层面：

| 原则 | 说明 |
|---|---|
| **单一职责** | 一个服务只负责一块业务，不要出现"什么都做"的服务 |
| **团队自治** | 一个团队（2 pizza team）能独立负责一个或几个服务的全生命周期 |
| **服务自治** | 服务独立部署、独立数据库、独立技术栈 |
| **粒度适中** | 拆得过细会导致调用链过长、运维成本爆炸，要控制拆分粒度 |

### (二) 黑马商城拆分案例

黑马商城 hmall 是一个典型的电商单体项目，按业务模块纵向拆分为：

| 服务名 | 职责 | 数据库 |
|---|---|---|
| `user-service` | 用户管理：登录、注册、个人信息 | `hm-user` |
| `item-service` | 商品管理：商品、库存、搜索 | `hm-item` |
| `cart-service` | 购物车 | `hm-cart` |
| `trade-service` | 交易：订单、下单流程 | `hm-trade` |
| `pay-service` | 支付：支付订单、退款 | `hm-pay` |

拆分时有两个硬性要求：

1. **不同微服务之间不要重复开发相同业务**（避免逻辑散落、修改遗漏）
2. **微服务数据独立，不要访问其它微服务的数据库**（跨库查询是微服务的大忌，只能通过接口调用）

### (三) 远程调用 —— RestTemplate

拆分后，购物车服务需要查询商品信息，而商品数据在 `item-service`，这就产生了**跨服务调用**。最简单的做法是使用 Spring 提供的 `RestTemplate` 发起 HTTP 请求。

**第一步：注册 `RestTemplate` 到 Spring 容器**

```java
@Configuration
public class RemoteCallConfig {

    @Bean
    public RestTemplate restTemplate() {
        return new RestTemplate();
    }
}
```

**第二步：发起远程调用**

```java
@Service
@RequiredArgsConstructor
public class CartServiceImpl extends ServiceImpl<CartMapper, Cart> implements ICartService {

    private final RestTemplate restTemplate;

    private void handleCartItems(List<CartVO> vos) {
        // 1. 收集商品 id
        Set<Long> itemIds = vos.stream().map(CartVO::getItemId).collect(Collectors.toSet());
        // 2. 远程查询商品信息
        ResponseEntity<List<ItemDTO>> response = restTemplate.exchange(
                "http://localhost:8081/items?ids={ids}",
                HttpMethod.GET,
                null,
                new ParameterizedTypeReference<List<ItemDTO>>() {},
                Map.of("ids", CollUtil.join(itemIds, ","))
        );
        List<ItemDTO> items = response.getBody();
        if (CollUtils.isEmpty(items)) {
            return;
        }
        // 3. 组装数据返回
        // ...
    }
}
```

> 注意：返回值为**泛型集合**时，必须使用 `exchange()` 配合 `ParameterizedTypeReference`，直接用 `getForObject` 会因为泛型擦除得到 `List<LinkedHashMap>`，强转成 `ItemDTO` 会抛类型转换异常。

### (四) 硬编码带来的问题

上面的写法中，服务的地址被硬编码在代码里，会引发一系列问题：

| 问题 | 描述 |
|---|---|
| 无法负载均衡 | 商品服务部署了 3 个实例，代码里只能写死访问其中一个 |
| 无法感知实例状态 | 某个实例宕机，调用方完全不知道，请求会持续失败 |
| 地址变更成本高 | 服务迁移、扩容后要修改所有调用方代码并重新发布 |

要解决这些问题，就需要引入**注册中心**，也就是下一章的 Nacos。

## 三、服务注册与发现 —— Nacos

### (一) 服务治理中的三个角色

| 角色 | 职责 |
|---|---|
| **服务提供者** | 暴露服务接口，供其它服务调用 |
| **服务消费者** | 调用其它服务提供的接口 |
| **注册中心** | 记录并监控微服务各实例状态，推送服务变更信息 |

两个核心问题：

- **消费者如何知道提供者的地址？**
  服务提供者会在启动时把自己的信息注册到注册中心，消费者可以从注册中心**订阅和拉取**服务信息。
- **消费者如何知道服务状态变更？**
  服务提供者通过**心跳机制**向注册中心报告自己的健康状态；当心跳异常时注册中心会将异常实例剔除，并**主动推送**变更信息给订阅了该服务的消费者。

> 当提供者有多个实例时，消费者可以通过**负载均衡算法**从多个实例中选择一个。

### (二) Nacos 简介与安装

Nacos（Dynamic Naming and Configuration Service）是阿里巴巴开源的服务注册与配置管理平台，一个组件同时承担了 **注册中心** 和 **配置中心** 两个角色。

**Docker 单机部署**（推荐方式）：

```bash
docker run -d \
  --name nacos \
  --env-file ./nacos/custom.env \
  -p 8848:8848 \
  -p 9848:9848 \
  -p 9849:9849 \
  --restart=always \
  nacos/nacos-server:v2.1.0-slim
```

`custom.env` 配置文件内容：

```properties
PREFER_HOST_MODE=hostname
MODE=standalone
SPRING_DATASOURCE_PLATFORM=mysql
MYSQL_SERVICE_HOST=192.168.150.101
MYSQL_SERVICE_DB_NAME=nacos
MYSQL_SERVICE_PORT=3306
MYSQL_SERVICE_USER=root
MYSQL_SERVICE_PASSWORD=123
MYSQL_SERVICE_DB_PARAM='characterEncoding=utf8&connectTimeout=1000&socketTimeout=3000&autoReconnect=true&useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=Asia/Shanghai'
```

Nacos 2.x 需要开放的端口（**缺一不可，否则客户端会报 9848 连接超时**）：

| 端口 | 与主端口偏移 | 作用 |
|---|---|---|
| 8848 | — | HTTP 主端口，控制台与 OpenAPI |
| 9848 | +1000 | gRPC：客户端向服务端发起连接和请求 |
| 9849 | +1001 | gRPC：服务端之间的通信 |
| 7848 | -1000 | 集群模式下 Raft 选举端口 |

安装成功后访问 `http://192.168.150.101:8848/nacos`，默认账号密码均为 `nacos`。

### (三) 服务注册

**第一步：引入依赖**

```xml
<!-- Nacos 服务注册发现 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
```

**第二步：配置 Nacos 地址与服务名**

```yaml
spring:
  application:
    name: item-service   # 服务名称，注册到 Nacos 的服务名
  cloud:
    nacos:
      server-addr: 192.168.150.101:8848
      discovery:
        cluster-name: HZ            # 集群名称
        namespace: 862cd2b5-xxxx    # 命名空间 ID（可选）
        group: DEFAULT_GROUP        # 分组（可选）
        ephemeral: true             # 是否为临时实例，默认 true
```

配置完成后启动服务，在 Nacos 控制台的「服务管理 → 服务列表」中即可看到注册上来的实例。

一个服务部署多个实例时，只需在启动配置中指定不同端口即可：

```bash
-Dserver.port=8081
-Dserver.port=8082
```

### (四) 服务发现与负载均衡

**第一步：给 `RestTemplate` 加上负载均衡能力**

```java
@Bean
@LoadBalanced   // 关键：开启服务名解析与负载均衡
public RestTemplate restTemplate() {
    return new RestTemplate();
}
```

**第二步：用服务名代替 IP + 端口发起调用**

```java
// 原来是硬编码：http://localhost:8081/items?ids=1
// 现在直接写服务名，由负载均衡器解析成真实地址
ResponseEntity<List<ItemDTO>> response = restTemplate.exchange(
        "http://item-service/items?ids={ids}",
        HttpMethod.GET,
        null,
        new ParameterizedTypeReference<List<ItemDTO>>() {},
        Map.of("ids", CollUtil.join(itemIds, ","))
);
```

也可以通过 `DiscoveryClient` 手动拉取实例列表（自定义负载策略时使用）：

```java
@RestController
@RequiredArgsConstructor
public class CartController {

    private final DiscoveryClient discoveryClient;

    @GetMapping("/instances")
    public List<ServiceInstance> getInstanceList() {
        return discoveryClient.getInstances("item-service");
    }
}
```

常用负载均衡规则：

| 组件 | 规则 | 说明 |
|---|---|---|
| Spring Cloud LoadBalancer | `RoundRobinLoadBalancer` | 轮询（默认） |
| Spring Cloud LoadBalancer | `RandomLoadBalancer` | 随机 |
| Ribbon（老版本） | `ZoneAvoidanceRule` | 区域优先 + 轮询 |
| Ribbon（老版本） | `WeightedResponseTimeRule` | 响应时间加权 |
| Nacos | `NacosRule` | **同集群优先**，同集群内随机 |

### (五) 分级存储模型与集群

Nacos 的服务存储模型是一棵树：**服务 → 集群 → 实例**。

```
Nacos
 └── namespace（命名空间，用于环境隔离）
      └── group（分组）
           └── service（服务，如 item-service）
                └── cluster（集群，如 HZ / SH）
                     └── instance（实例，如 8081 / 8082）
```

为什么要分集群？一个服务往往有多个实例，为了容纳这些实例会部署在不同的机房。服务调用时应**尽可能访问本地集群（同机房）**，跨机房调用延迟高；只有当本地集群不可用时，才去访问其它集群。

配置集群名称：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        cluster-name: HZ   # 配置所属集群，例如杭州机房
```

配置同集群优先的负载均衡规则（消费者侧）：

```yaml
item-service:   # 被调用的服务名
  ribbon:
    NFLoadBalancerRuleClassName: com.alibaba.cloud.nacos.ribbon.NacosRule
```

或者使用全局配置（Spring Cloud 2020+ 写法）：

```java
@Bean
public IRule nacosRule() {
    return new NacosRule();
}
```

`NacosRule` 的特点：**优先选择同集群实例**；同集群内多个实例之间**随机选择**；当本地集群找不到可用实例时，才会跨集群访问，并在日志中给出警告。

### (六) 权重配置与优雅上下线

在 Nacos 控制台可以调整实例的**权重**，取值范围 `0 ~ 1`：

- 权重越大，被访问的频率越高
- **权重设为 0，该实例完全不会被访问**

利用权重为 0 可以实现**平滑升级**：

1. 将要升级的实例权重调整为 0，流量全部切走
2. 停止该实例，部署新版本
3. 新实例启动后，先把权重调成很小的值（如 0.05），小流量灰度验证
4. 确认无误后逐步调大权重，直至恢复正常值

### (七) 环境隔离 —— namespace

Nacos 中服务存储和数据存储的最外层都是 **namespace**，用来做最外层隔离，最常见的用法就是**环境隔离**（dev / test / prod）。

- 每个 namespace 都有唯一 ID
- **不同 namespace 下的服务互相不可见**，无法互相调用
- 服务配置时必须指定 `namespace` 的 **ID**，而不是名称

控制台新建命名空间后，在配置中引用：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        namespace: 862cd2b5-3f4a-4b2e-a1c1-xxxxxxxxxxxx  # 命名空间 ID
```

> 注意区分：`namespace` 做环境隔离，`group` 做服务分组隔离，二者组合使用可以满足绝大多数多环境、多租户场景。

### (八) Nacos 与 Eureka 的对比

| 对比项 | Nacos | Eureka |
|---|---|---|
| 服务发现模式 | 定时拉取 + **服务端主动推送**（UDP/gRPC） | 定时拉取（默认 30s） |
| 健康检查 | 临时实例心跳 / 非临时实例**服务端主动探测** | 仅客户端心跳 |
| 一致性 | 默认 AP；存在非临时实例时切换为 CP | AP |
| 配置管理 | **内置配置中心**，支持热更新 | 无，需配合 Config |
| 实例权重 | 支持 | 不支持 |
| 停服后表现 | 临时实例被剔除；非临时实例保留并标记不健康 | 剔除实例 |

Nacos 的实例类型：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        ephemeral: true    # true：临时实例（默认），心跳停止则剔除
                           # false：非临时实例，Nacos 主动探活，不会被剔除，只标记不健康
```

临时实例与非临时实例的关键区别：临时实例一旦宕机就会从服务列表中剔除；非临时实例宕机后仍保留在服务列表中，只是标记为不健康，适合需要保留实例信息的场景（如运维排查）。

## 四、统一配置管理 —— Nacos Config

### (一) 为什么需要配置中心

微服务动辄几十上百个服务，每个服务都有大量配置，且很多配置是**重复的**（如数据库连接、Redis 地址、日志级别）。如果还沿用本地 `application.yml`，会带来：

| 问题 | 说明 |
|---|---|
| 配置分散 | 修改一个公共配置要挨个服务改一遍 |
| 修改需重启 | 改完配置必须重新打包发布才能生效 |
| 无版本管理 | 谁改的、改成了什么、什么时候改的，无从追溯 |

配置中心的思路：把**需要动态调整、被多个服务共享**的配置统一放到 Nacos 管理，微服务启动时从 Nacos 拉取，并**监听配置变更实现热更新**。

### (二) 配置文件的 dataId 规则

Nacos 中一个配置由 `namespace` + `group` + `dataId` 唯一定位。`dataId` 的完整格式为：

```
${prefix}-${spring.profiles.active}.${file-extension}
```

| 组成 | 默认值 | 说明 |
|---|---|---|
| `prefix` | `spring.application.name` | 可用 `spring.cloud.nacos.config.prefix` 覆盖 |
| `spring.profiles.active` | 空 | 当前环境，`-dev`、`-test` 等 |
| `file-extension` | `properties` | 配置格式，常用 `yaml` |

举例：服务名为 `userservice`，环境为 `dev`，格式为 `yaml`，则 `dataId = userservice-dev.yaml`。

> 注意：Nacos 中 `dataId` 必须带后缀（`yaml` 或 `properties`），否则拉取不到配置。

### (三) 微服务拉取配置

**Spring Boot 3.x（推荐写法，使用 `spring.config.import`）**

```yaml
spring:
  application:
    name: cart-service
  profiles:
    active: dev
  cloud:
    nacos:
      server-addr: 192.168.150.101:8848
      config:
        file-extension: yaml
        namespace: 862cd2b5-3f4a-4b2e-a1c1-xxxxxxxxxxxx
        group: DEFAULT_GROUP
  config:
    import:
      - nacos:${spring.application.name}-${spring.profiles.active}.${spring.cloud.nacos.config.file-extension}
      - nacos:shared-jdbc.yaml      # 共享配置
      - nacos:shared-log.yaml
```

**Spring Boot 2.x（使用 `bootstrap.yml`）**

Spring Boot 2.4 之后默认不再加载 `bootstrap.yml`，需要额外引入依赖：

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-bootstrap</artifactId>
</dependency>
```

`bootstrap.yml` 内容（ **引导文件，加载优先级高于 `application.yml`** ）：

```yaml
spring:
  application:
    name: cart-service
  profiles:
    active: dev
  cloud:
    nacos:
      server-addr: 192.168.150.101:8848
      config:
        file-extension: yaml
        namespace: 862cd2b5-3f4a-4b2e-a1c1-xxxxxxxxxxxx
        shared-configs:       # 共享配置
          - dataId: shared-jdbc.yaml
            refresh: true
        extension-configs:    # 扩展配置
          - dataId: shared-log.yaml
            refresh: true
```

依赖：

```xml
<!-- Nacos 配置管理 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>
```

> 注意：Nacos 地址、服务名这类"用于拉取配置的配置"必须写在优先级更高的位置（`bootstrap.yml` 或 `spring.config.import`），不能写在 `application.yml`，否则会因为还没拿到 Nacos 地址而无法拉取。

### (四) 配置热更新

配置中心最大的价值是**改完配置不用重启服务**。实现方式有两种：

**方式一：`@RefreshScope` + `@Value`（简单，适合零散配置）**

```java
@RestController
@RefreshScope   // 开启配置热更新，配置变更时重建该 Bean
public class TestController {

    @Value("${hm.test.value}")
    private String value;

    @GetMapping("/test")
    public String test() {
        return value;
    }
}
```

**方式二：`@ConfigurationProperties` + `@Component`（推荐，适合一组配置）**

```java
@Data
@Component
@ConfigurationProperties(prefix = "hm.cart")
public class CartProperties {
    /**
     * 购物车中单个商品的最大数量
     */
    private Integer maxItems;
}
```

Nacos 中的配置：

```yaml
hm:
  cart:
    maxItems: 10
```

> 推荐原因：`@ConfigurationProperties` 本身就是**自动刷新**的，不需要加 `@RefreshScope`；而且它把一组相关配置封装成一个对象，类型安全、有 IDE 提示，比散落各处的 `@Value` 更易于维护。

### (五) 配置共享与优先级

一个微服务通常会加载多份配置，出现相同 key 时的优先级从高到低为：

```
服务名-profile.yaml            （如 cart-service-dev.yaml，环境专属，优先级最高）
      ↓
服务名.yaml                    （如 cart-service.yaml，服务专属）
      ↓
extension-configs              （扩展配置，数组下标越大优先级越高）
      ↓
shared-configs                 （共享配置，数组下标越大优先级越高）
      ↓
本地 application.yml           （优先级最低）
```

典型用法：把**数据库连接、Redis、日志、MQ** 这些所有服务都一样的配置抽成 `shared-xxx.yaml`，把**个别服务特有的**配置放在 `服务名.yaml`，把**环境差异**配置放在 `服务名-profile.yaml`。

### (六) 动态路由

除了业务配置，**Gateway 的路由表**也适合放到 Nacos 管理，实现"新增一个服务不用改网关配置、不用重启网关"。

**第一步：在 Nacos 中添加路由配置 `gateway-routes.json`**

配置格式选择 `JSON`：

```json
[
    {
        "id": "item",
        "predicates": [
            {
                "name": "Path",
                "args": {"_genkey_0": "/items/**", "_genkey_1": "/search/**"}
            }
        ],
        "filters": [],
        "uri": "lb://item-service"
    },
    {
        "id": "cart",
        "predicates": [
            {
                "name": "Path",
                "args": {"_genkey_0": "/carts/**"}
            }
        ],
        "filters": [],
        "uri": "lb://cart-service"
    }
]
```

**第二步：监听 Nacos 配置变更并刷新路由表**

```java
@Slf4j
@Component
@RequiredArgsConstructor
public class DynamicRouteLoader {

    private final RouteDefinitionWriter writer;
    private final NacosConfigManager nacosConfigManager;

    // 路由配置的 dataId 与 group
    private final String dataId = "gateway-routes.json";
    private final String group = "DEFAULT_GROUP";
    // 保存已更新的路由 id，便于删除
    private final Set<String> routeIds = new HashSet<>();

    @PostConstruct
    public void initRouteConfigListener() throws NacosException {
        // 1. 项目启动时先拉取一次配置，并注册配置监听器
        String configInfo = nacosConfigManager.getConfigService()
                .getConfigAndSignListener(dataId, group, 5000, new Listener() {
                    @Override
                    public Executor getExecutor() {
                        return null;
                    }

                    @Override
                    public void receiveConfigInfo(String configInfo) {
                        // 2. 配置变更时更新路由表
                        updateConfigInfo(configInfo);
                    }
                });
        // 3. 首次读取到的配置也需要更新到路由表
        updateConfigInfo(configInfo);
    }

    public void updateConfigInfo(String configInfo) {
        log.info("监听到路由配置变更：{}", configInfo);
        // 1. 解析配置信息，转为 RouteDefinition
        List<RouteDefinition> routeDefinitions = JSONUtil.toList(configInfo, RouteDefinition.class);
        // 2. 删除旧的路由表
        for (String routeId : routeIds) {
            writer.delete(Mono.just(routeId)).subscribe();
        }
        routeIds.clear();
        // 3. 更新路由表
        for (RouteDefinition routeDefinition : routeDefinitions) {
            writer.save(Mono.just(routeDefinition)).subscribe();
            routeIds.add(routeDefinition.getId());
        }
    }
}
```

> 注意：使用 `spring.config.import` 引入 `gateway-routes.json` 时，需要指定 `refresh-enabled: true` 或通过上述监听器方式手动刷新；JSON 中 `predicates` 的 `args` 里的 key 是 `_genkey_0`、`_genkey_1` 这种固定写法，不能自定义。

## 五、远程调用 —— OpenFeign

`RestTemplate` 方式存在明显问题：拼接 URL 麻烦、代码可读性差、参数复杂时难以维护。OpenFeign 是一个**声明式 HTTP 客户端**，只需要定义一个接口并加注解，就能像调用本地方法一样完成远程调用，底层自动完成服务名解析、负载均衡、请求发送与响应解析。

### (一) 快速入门

**第一步：引入依赖**

```xml
<!-- OpenFeign -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-openfeign</artifactId>
</dependency>
<!-- 负载均衡器（Spring Cloud 2020 之后必须显式引入） -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>
```

**第二步：启用 Feign 客户端**

```java
@EnableFeignClients(basePackages = "com.hmall.api.client")
@MapperScan("com.hmall.cart.mapper")
@SpringBootApplication
public class CartApplication {
    public static void main(String[] args) {
        SpringApplication.run(CartApplication.class, args);
    }
}
```

**第三步：编写 Feign 客户端接口**

```java
@FeignClient("item-service")   // 声明要调用的服务名
public interface ItemClient {

    @GetMapping("/items")
    List<ItemDTO> queryItemByIds(@RequestParam("ids") Collection<Long> ids);

    @PutMapping("/items/stock/deduct")
    void deductStock(@RequestBody List<OrderDetailDTO> items);
}
```

**第四步：像调用本地方法一样使用**

```java
@Service
@RequiredArgsConstructor
public class CartServiceImpl extends ServiceImpl<CartMapper, Cart> implements ICartService {

    private final ItemClient itemClient;

    private void handleCartItems(List<CartVO> vos) {
        Set<Long> itemIds = vos.stream().map(CartVO::getItemId).collect(Collectors.toSet());
        // 一行代码完成远程调用，无需关心 URL、负载均衡、序列化
        List<ItemDTO> items = itemClient.queryItemByIds(itemIds);
        // ...
    }
}
```

编写 Feign 接口时的注意点：

| 注意点 | 说明 |
|---|---|
| `@FeignClient` 的值 | 填**服务名**，配合注册中心使用；也可以用 `url` 属性指定固定地址 |
| 请求方式 | 必须使用 SpringMVC 注解：`@GetMapping` / `@PostMapping` 等 |
| 参数绑定 | `@RequestParam`、`@PathVariable`、`@RequestBody` **不能省略** |
| 参数名 | `@RequestParam("ids")` 中的名称必须写，否则会丢参数 |
| 方法路径 | 必须与提供者的 Controller 路径完全一致 |

### (二) 连接池

Feign 底层默认使用 JDK 自带的 `HttpURLConnection` 发请求，**不支持连接池**，每次调用都要新建连接，性能较差且容易耗尽端口。生产环境必须替换成支持连接池的客户端。

**方案一：OKHttp（推荐）**

```xml
<dependency>
    <groupId>io.github.openfeign</groupId>
    <artifactId>feign-okhttp</artifactId>
</dependency>
```

```yaml
feign:
  okhttp:
    enabled: true      # 开启 OKHttp 连接池
```

**方案二：Apache HttpClient**

```xml
<dependency>
    <groupId>io.github.openfeign</groupId>
    <artifactId>feign-httpclient</artifactId>
</dependency>
```

```yaml
feign:
  httpclient:
    enabled: true           # 开启 HttpClient 连接池
    max-connections: 200    # 最大连接数
    max-connections-per-route: 50   # 每个路径的最大连接数
```

> 两个连接池二选一即可，不要同时开启。开启后建议配合日志级别 `BASIC` 观察是否生效。

### (三) 最佳实践 —— 抽取独立模块

如果每个微服务都自己写一份 Feign 接口，会出现**大量重复代码**（多个服务都要调用 `item-service`）。黑马课程给出两种方案：

**方案一：继承（不推荐）**

给消费者的 `FeignClient` 和提供者的 `Controller` 定义一个统一的父接口作为标准：

```java
public interface UserAPI {
    @GetMapping("/user/{id}")
    User findById(@PathVariable("id") Long id);
}

// 消费者
@FeignClient("user-service")
public interface UserClient extends UserAPI { }

// 提供者
@RestController
public class UserController implements UserAPI { ... }
```

缺点是**紧耦合**（服务提供方和消费方要共用同一套接口定义），且 SpringMVC 的注解在接口继承中容易出问题，官方不推荐。

**方案二：抽取（推荐）**

思路：将 `FeignClient`、相关 DTO、**默认的 Feign 配置**全部抽取到一个**独立模块**（如 `hm-api`），所有需要调用的服务引入这个模块即可。

模块结构：

```
hm-api
 └── src/main/java/com/hmall/api
      ├── client
      │    ├── ItemClient.java
      │    ├── CartClient.java
      │    └── config
      │         └── DefaultFeignConfig.java
      └── domain
           ├── dto
           │    ├── ItemDTO.java
           │    └── OrderDetailDTO.java
           └── po
                └── Order.java
```

**1. 抽取配置类**

```java
// 注意：这个类不要放在启动类的扫描包下，避免对所有 FeignClient 全局生效
@Slf4j
public class DefaultFeignConfig {

    @Bean
    public Logger.Level feignLoggerLevel() {
        return Logger.Level.FULL;
    }

    @Bean
    public RequestInterceptor userInfoRequestInterceptor() {
        return template -> {
            Long userId = UserContext.getUser();
            if (userId != null) {
                template.header("user-info", userId.toString());
            }
        };
    }
}
```

**2. 消费方引入并使用**

```xml
<dependency>
    <groupId>com.heima</groupId>
    <artifactId>hm-api</artifactId>
    <version>1.0.0</version>
</dependency>
```

```java
// 第二个参数指定默认配置，basePackages 指定 FeignClient 所在包
@EnableFeignClients(basePackages = "com.hmall.api.client",
                   defaultConfiguration = DefaultFeignConfig.class)
@SpringBootApplication
public class TradeApplication {
    public static void main(String[] args) {
        SpringApplication.run(TradeApplication.class, args);
    }
}
```

> 关键点：当 `@FeignClient` 不在启动类的扫描路径下时，必须通过 `@EnableFeignClients` 的 `basePackages` 或 `clients` 属性显式声明，否则注入时会报 `NoSuchBeanDefinitionException`。

**3. 提供方保持接口一致**

提供方引入 `hm-api` 后，Controller 的方法签名、路径与 `client` 中的接口保持一致（注意：**SpringMVC 的映射注解不会从接口继承**，Controller 上的 `@GetMapping` 等注解仍需自己声明），这样编译期就能发现路径不一致的问题。

### (四) 日志配置

OpenFeign 的日志级别有四种：

| 级别 | 打印内容 | 适用场景 |
|---|---|---|
| `NONE` | 不记录任何日志（**默认**） | 生产环境 |
| `BASIC` | 仅记录请求方法、URL、响应状态码、执行时间 | 生产环境 |
| `HEADERS` | 在 BASIC 基础上，记录请求和响应头 | 排查问题 |
| `FULL` | 记录请求/响应的 header、body、元数据 | 开发/测试环境 |

**方式一：配置文件**

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          default:              # default 表示全局；也可写具体服务名做细粒度配置
            logger-level: FULL
            connect-timeout: 1000
            read-timeout: 2000
```

**方式二：Java 配置类**

```java
@Configuration
public class FeignConfig {

    @Bean
    public Logger.Level feignLoggerLevel() {
        return Logger.Level.FULL;
    }
}
```

> 注意：Feign 的日志是通过 `debug` 级别输出的，**必须把对应包的日志级别调成 DEBUG 才能看到日志**：
>
> ```yaml
> logging:
>   level:
>     com.hmall.api.client: DEBUG
> ```

### (五) 超时控制与重试

**超时配置**

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            connect-timeout: 1000     # 连接超时（建立 TCP 连接的时间）
            read-timeout: 2000        # 读取超时（等待响应返回的时间）
```

也可以针对单个服务单独设置：

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          item-service:              # 只对调用 item-service 生效
            connect-timeout: 500
            read-timeout: 5000
```

> 生产建议：超时时间必须**小于**上游服务的超时时间，避免层层叠加导致线程堆积；查询类接口可以设置较短的读超时，下单、支付等写操作可以适当放宽。

**重试配置**

Spring Cloud 2020 之后 Ribbon 已被移除，重试需要引入 `spring-retry` 并使用 Spring Cloud LoadBalancer 的重试机制：

```xml
<dependency>
    <groupId>org.springframework.retry</groupId>
    <artifactId>spring-retry</artifactId>
</dependency>
```

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            retryer: feign.Retryer.Default   # 使用 Feign 默认重试器（默认重试 5 次，间隔 100ms 起）
    loadbalancer:
      retry:
        enabled: true        # 开启负载均衡层的重试（失败后换一个实例重试）
```

> 注意：重试只对**幂等**操作开启。查询可以重试，下单、扣库存这类写操作重试会导致重复提交，必须配合幂等设计（唯一索引、Token 机制）或关闭重试。

### (六) 熔断降级 —— Fallback

当被调用服务不可用或响应时间过长时，不应该让异常直接抛给用户，而应该返回一个**降级结果**（兜底数据）。新版本 Spring Cloud 通过 **Resilience4j** 实现，OpenFeign 提供了整合入口。

**第一步：开启熔断**

```yaml
spring:
  cloud:
    openfeign:
      circuitbreaker:
        enabled: true     # 开启熔断支持
```

**第二步：编写 FallbackFactory（推荐，能拿到异常信息）**

```java
@Slf4j
public class ItemClientFallbackFactory implements FallbackFactory<ItemClient> {

    @Override
    public ItemClient create(Throwable cause) {
        return new ItemClient() {
            @Override
            public List<ItemDTO> queryItemByIds(Collection<Long> ids) {
                log.error("远程调用 item-service 查询商品失败，执行降级逻辑", cause);
                return CollUtils.emptyList();   // 返回空集合作为兜底
            }

            @Override
            public void deductStock(List<OrderDetailDTO> items) {
                throw new BizIllegalException("库存扣减失败，请稍后重试");
            }
        };
    }
}
```

**第三步：注册为 Bean 并在 `@FeignClient` 中引用**

```java
@Bean
public ItemClientFallbackFactory itemClientFallbackFactory() {
    return new ItemClientFallbackFactory();
}
```

```java
@FeignClient(value = "item-service", fallbackFactory = ItemClientFallbackFactory.class)
public interface ItemClient {
    // ...
}
```

对比两种降级方式：

| 方式 | 能否获取异常 | 说明 |
|---|---|---|
| `fallback = XxxFallback.class` | 不能 | 实现 Feign 接口，返回兜底数据 |
| `fallbackFactory = XxxFallbackFactory.class` | **能** | 可打印日志、按异常类型返回不同结果，推荐使用 |

## 六、服务网关 —— Spring Cloud Gateway

### (一) 为什么需要网关

没有网关时，前端需要记住每一个微服务的地址，且**每个服务都要重复实现登录校验**，架构混乱。

网关的核心作用：

| 作用 | 说明 |
|---|---|
| **统一入口** | 前端只访问网关，由网关把请求路由到具体服务 |
| **路由转发** | 根据请求路径等条件，把请求转发到对应微服务 |
| **负载均衡** | 通过 `lb://服务名` 自动实现实例选择与负载均衡 |
| **统一鉴权** | 登录校验、权限校验集中实现，业务服务不必重复开发 |
| **流量控制** | 限流、熔断、降级统一在入口层处理 |
| **跨域处理** | 统一配置 CORS，避免每个服务各配一遍 |

### (二) 快速入门

**第一步：创建网关模块并引入依赖**

```xml
<!-- 网关 -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-gateway</artifactId>
</dependency>
<!-- Nacos 服务发现：支持 lb:// 路由 -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
</dependency>
<!-- 负载均衡 -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>
```

> ⚠️ 重要：Spring Cloud Gateway 基于 **WebFlux（响应式）** 实现，**不能引入 `spring-boot-starter-web`**，两者会冲突导致启动失败。

**第二步：编写启动类**

```java
@SpringBootApplication
public class GatewayApplication {
    public static void main(String[] args) {
        SpringApplication.run(GatewayApplication.class, args);
    }
}
```

**第三步：配置路由**

```yaml
server:
  port: 8080

spring:
  application:
    name: gateway
  cloud:
    nacos:
      server-addr: 192.168.150.101:8848
    gateway:
      routes:
        - id: item            # 路由 id，自定义，唯一即可
          uri: lb://item-service   # 目标地址，lb 表示负载均衡
          predicates:              # 路由断言，判断请求是否匹配该路由
            - Path=/items/**,/search/**
        - id: cart
          uri: lb://cart-service
          predicates:
            - Path=/carts/**
        - id: user
          uri: lb://user-service
          predicates:
            - Path=/users/**,/addresses/**
        - id: trade
          uri: lb://trade-service
          predicates:
            - Path=/orders/**
        - id: pay
          uri: lb://pay-service
          predicates:
            - Path=/pay-orders/**
```

配置完成后，访问 `http://localhost:8080/items/10001` 即可由网关转发到 `item-service`。

### (三) 路由的四要素

一条完整的路由由四部分组成：

| 属性 | 说明 | 示例 |
|---|---|---|
| `id` | 路由唯一标识 | `item` |
| `uri` | 目标地址，`lb://` 前缀表示从注册中心负载均衡，`http://` 表示固定地址 | `lb://item-service` |
| `predicates` | 路由断言，判断请求是否走这条路由（可配多个，全部满足才匹配） | `- Path=/items/**` |
| `filters` | 路由过滤器，对请求或响应做处理（可配多个） | `- StripPrefix=1` |
| `order` | 路由优先级，数值越小优先级越高 | `0` |

**uri 的两种写法**

```yaml
uri: lb://item-service          # 负载均衡到服务实例（推荐）
uri: http://127.0.0.1:8081      # 固定地址，不推荐，丧失了弹性伸缩能力
```

> 使用 `lb://` 时，**必须引入 `spring-cloud-starter-loadbalancer`**，否则报 `Unable to find instance`。

### (四) 路由断言工厂

`predicates` 中配置的断言，会被 **Route Predicate Factory** 解析成具体的判断条件。Spring Cloud Gateway 内置了如下断言工厂：

| 断言工厂 | 说明 | 示例 |
|---|---|---|
| `Path` | 路径匹配（最常用，支持 Ant 风格） | `- Path=/items/**` |
| `After` | 请求时间在指定时间之后 | `- After=2030-01-20T17:42:47.789+08:00[Asia/Shanghai]` |
| `Before` | 请求时间在指定时间之前 | `- Before=2030-01-20T17:42:47.789+08:00` |
| `Between` | 请求时间在指定时间区间内 | `- Between=2030-01-20T17:42:47+08:00, 2030-01-21T17:42:47+08:00` |
| `Method` | 请求方式匹配 | `- Method=GET,POST` |
| `Header` | 请求头匹配（第二个参数为正则） | `- Header=X-Request-Id, \d+` |
| `Query` | 请求参数匹配 | `- Query=name, jack` |
| `Cookie` | Cookie 匹配 | `- Cookie=sessionId, [a-z]+` |
| `Host` | 域名匹配 | `- Host=**.hmall.com` |
| `RemoteAddr` | 来源 IP 匹配（支持 CIDR） | `- RemoteAddr=192.168.1.1/24` |
| `Weight` | 按权重分流 | `- Weight=group1, 8` |

一个组合使用的例子：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: item-vip
          uri: lb://item-service
          predicates:
            - Path=/items/**
            - Method=GET
            - Header=X-Request-Source, app
          order: 1
```

### (五) 路由过滤器工厂

`filters` 中配置的过滤器，由 **GatewayFilter Factory** 生成，用于对请求或响应做加工。常用的内置过滤器工厂：

| 过滤器工厂 | 说明 | 示例 |
|---|---|---|
| `AddRequestHeader` | 添加请求头 | `- AddRequestHeader=X-Request-Name, hm` |
| `RemoveRequestHeader` | 移除请求头 | `- RemoveRequestHeader=X-Request-Source` |
| `AddRequestParameter` | 添加请求参数 | `- AddRequestParameter=name, jack` |
| `AddResponseHeader` | 添加响应头 | `- AddResponseHeader=X-Response-Name, hm` |
| `StripPrefix` | 去除路径前缀（n 段） | `- StripPrefix=1` |
| `PrefixPath` | 添加路径前缀 | `- PrefixPath=/api` |
| `RewritePath` | 路径重写（正则） | `- RewritePath=/api/(?<segment>.*), /${segment}` |
| `RedirectTo` | 重定向 | `- RedirectTo=302, https://www.baidu.com` |
| `SetStatus` | 设置响应状态码 | `- SetStatus=401` |
| `Retry` | 请求重试 | `- Retry=3` |
| `CircuitBreaker` | 熔断降级 | `- CircuitBreaker=myCircuitBreaker` |
| `RequestRateLimiter` | 基于令牌桶限流 | 需配合 Redis |

配置示例：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: item
          uri: lb://item-service
          predicates:
            - Path=/items/**
          filters:
            - AddRequestHeader=X-Request-Source, gateway
            - StripPrefix=1
      default-filters:      # 默认过滤器，对**所有**路由生效
        - AddRequestHeader=truth, everyone-is-the-best
```

### (六) 全局过滤器 —— 统一登录校验

路由过滤器只能按固定规则加工请求，而**登录校验这类有业务逻辑的判断**需要自定义 `GlobalFilter`。

**第一步：编写配置属性类（读取白名单路径）**

```yaml
hm:
  auth:
    excludePaths:
      - /search/**
      - /users/login
      - /items/**
      - /hi
```

```java
@Data
@Component
@ConfigurationProperties(prefix = "hm.auth")
public class AuthProperties {
    private List<String> excludePaths;
}
```

**第二步：实现 GlobalFilter**

```java
@Component
@RequiredArgsConstructor
@EnableConfigurationProperties(AuthProperties.class)
public class AuthGlobalFilter implements GlobalFilter, Ordered {

    private final AuthProperties authProperties;
    private final JwtTool jwtTool;
    private final AntPathMatcher antPathMatcher = new AntPathMatcher();

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        // 1. 获取请求对象
        ServerHttpRequest request = exchange.getRequest();
        // 2. 判断是否需要做登录拦截
        if (isExclude(request.getPath().toString())) {
            // 白名单路径，直接放行
            return chain.filter(exchange);
        }
        // 3. 获取 token
        String token = null;
        List<String> headers = request.getHeaders().get("authorization");
        if (headers != null && !headers.isEmpty()) {
            token = headers.get(0);
        }
        // 4. 校验并解析 token
        Long userId = null;
        try {
            userId = jwtTool.parseToken(token);
        } catch (UnauthorizedException e) {
            // 5. 校验失败，拦截并返回 401
            ServerHttpResponse response = exchange.getResponse();
            response.setRawStatusCode(HttpStatus.UNAUTHORIZED.value());
            return response.setComplete();
        }
        // 6. 校验通过，把用户信息放到请求头，传递给下游微服务
        ServerWebExchange swe = exchange.mutate()
                .request(builder -> builder.header("user-info", userId.toString()))
                .build();
        // 7. 放行
        return chain.filter(swe);
    }

    private boolean isExclude(String path) {
        for (String pathPattern : authProperties.getExcludePaths()) {
            if (antPathMatcher.match(pathPattern, path)) {
                return true;
            }
        }
        return false;
    }

    @Override
    public int getOrder() {
        return 0;   // 数值越小，优先级越高
    }
}
```

> 关键点：`ServerHttpRequest` 是**只读对象**，不能直接 `setHeader`，必须通过 `exchange.mutate().request(builder -> ...).build()` 生成新的 exchange，再 `chain.filter(新exchange)` 继续传递。

### (七) 网关 → 微服务：获取用户信息

网关在请求头里塞了 `user-info`，下游微服务需要把它取出来。由于一个服务中很多地方都要用到当前用户，常用方案是**拦截器 + ThreadLocal**。

**第一步：定义用户上下文（ThreadLocal）**

```java
public class UserContext {
    private static final ThreadLocal<Long> TL = new ThreadLocal<>();

    public static void setUser(Long userId) {
        TL.set(userId);
    }

    public static Long getUser() {
        return TL.get();
    }

    public static void removeUser() {
        TL.remove();   // 务必清理，线程池复用线程会造成数据污染
    }
}
```

**第二步：编写 SpringMVC 拦截器**

```java
@Slf4j
public class UserInfoInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // 1. 获取登录用户信息
        String userInfo = request.getHeader("user-info");
        // 2. 判断是否获取了用户，如果有，存入 ThreadLocal
        if (StrUtil.isNotBlank(userInfo)) {
            UserContext.setUser(Long.valueOf(userInfo));
        }
        // 3. 放行
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        // 请求结束后务必清理，防止内存泄漏与用户信息错乱
        UserContext.removeUser();
    }
}
```

**第三步：注册拦截器**

```java
@Configuration
@ConditionalOnClass(DispatcherServlet.class)   // 网关是 WebFlux，没有 DispatcherServlet，可避免冲突
public class MvcConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new UserInfoInterceptor())
                .addPathPatterns("/**");
    }
}
```

> 由于微服务可能会把公共拦截器抽到 `common` 模块，而网关也会依赖 `common`，因此网关侧需要用 `@ConditionalOnClass(DispatcherServlet.class)` 判断当前是 WebFlux 还是 WebMVC，避免注册不存在的组件。

### (八) 微服务 → OpenFeign：透传用户信息

微服务内部通过 OpenFeign 调用其它服务时，**请求头不会自动传递**，所以需要 `RequestInterceptor` 把 `UserContext` 中的用户信息写到 Feign 的请求模板上。

```java
public class DefaultFeignConfig {

    @Bean
    public RequestInterceptor userInfoRequestInterceptor() {
        return new RequestInterceptor() {
            @Override
            public void apply(RequestTemplate template) {
                Long userId = UserContext.getUser();
                if (userId != null) {
                    template.header("user-info", userId.toString());
                }
            }
        };
    }
}
```

在启动类上引用：

```java
@EnableFeignClients(basePackages = "com.hmall.api.client",
                   defaultConfiguration = DefaultFeignConfig.class)
@SpringBootApplication
public class TradeApplication { ... }
```

> 注意：这个配置类不加 `@Configuration`，而是作为 `defaultConfiguration` 显式传入，这样它只作用于本服务的 Feign 客户端，不会污染 Spring 容器中的其它 Bean（例如不会对所有 `RestTemplate` 生效）。

至此，整条链路的用户信息传递打通：

```
前端请求(带 token)
   ↓
网关：GlobalFilter 校验 token → 解析 userId → 写入请求头 user-info
   ↓
微服务 A：HandlerInterceptor 读取 user-info → 存入 UserContext(ThreadLocal)
   ↓
微服务 A --OpenFeign RequestInterceptor--> 微服务 B（请求头带上 user-info）
   ↓
微服务 B：HandlerInterceptor 读取 → 存入自己的 UserContext
```

### (九) 过滤器的执行顺序

网关中存在三类过滤器，它们最终合并到同一个过滤器链中，按 `order` 值从小到大排序执行：

| 类型 | 作用范围 | 来源 |
|---|---|---|
| `default-filters` | 对所有路由生效 | 配置文件中的 `default-filters` |
| 路由过滤器 | 只对当前路由生效 | 每个 route 下的 `filters` |
| `GlobalFilter` | 对所有路由生效 | 自定义代码实现 `Ordered` |

三条排序规则：

1. 每个过滤器都必须指定一个 `order`，**order 值越小，优先级越高，越先执行**
2. 路由过滤器和 `defaultFilter` 的 order 由 Spring 自动指定，默认按声明顺序**从 1 开始递增**
3. **当 order 值相同时**，执行优先级为：`defaultFilter` > 路由过滤器 > `GlobalFilter`

查看方式：给网关加日志配置，启动时可以看到每个过滤器的实际顺序：

```yaml
logging:
  level:
    org.springframework.cloud.gateway: DEBUG
```

## 七、微服务保护 —— Sentinel

### (一) 雪崩问题及其解决方案

**雪崩问题**：微服务调用链路中，某个服务出现故障（响应变慢或不可用），导致调用它的服务线程被大量占用、资源耗尽，进而引发**故障逐级向上放大**，最终整个系统瘫痪。

举例：服务 A → 服务 B → 服务 C，C 故障后 B 的请求全部阻塞，B 的线程池被占满后 A 也扛不住，最终整条链路全挂。

业界有四种通用解决方案：

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **超时处理** | 设定超时时间，请求超过一定时间就返回错误信息 | 简单，释放资源快 | 只能缓解，请求量大时依然会堆积 |
| **舱壁模式** | 限定每个业务能使用的线程数，避免耗尽整个 Tomcat 资源 | 故障被隔离在单个业务内 | 资源仍然被占用一段时间 |
| **熔断降级** | 由**断路器**统计异常比例，超过阈值就熔断该业务，拦截一切请求快速失败 | 快速失败，保护调用方 | 需要合理的阈值配置 |
| **流量控制** | 限制业务访问的 QPS，避免服务因流量突增而故障 | 预防性保护 | 超出流量的请求会被拒绝 |

> 一个形象的比喻：把"限流"看作**预防**，把"超时、隔离、熔断"看作**治疗**。生产环境通常四者组合使用。

### (二) Sentinel 简介

Sentinel 是阿里巴巴开源的**流量控制、熔断降级**组件，与 Hystrix 相比优势明显：

| 对比项 | Sentinel | Hystrix |
|---|---|---|
| 隔离策略 | **信号量隔离** | 线程池隔离 / 信号量隔离 |
| 熔断策略 | 慢调用比例、异常比例、异常数 | 异常比例 |
| 限流 | 支持 QPS、线程数、多种模式与效果 | 有限支持 |
| 配置方式 | **控制台实时推送，实时生效** | 需要代码或配置中心 |
| 控制台 | 开箱即用，支持机器发现、实时监控 | 需自行搭建 Dashboard |

**启动 Sentinel 控制台**

```bash
java -Dserver.port=8090 \
     -Dcsp.sentinel.dashboard.server=localhost:8090 \
     -Dproject.name=sentinel-dashboard \
     -jar sentinel-dashboard-1.8.6.jar
```

访问 `http://localhost:8090`，默认账号密码均为 `sentinel`。

> 注意：Sentinel 控制台是**懒加载**的，服务启动后必须**先访问一次接口**，才能在控制台看到该服务的簇点链路。

### (三) 微服务整合 Sentinel

**第一步：引入依赖**

```xml
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>

```

**第二步：配置控制台地址**

```yaml
      http-method-specify: true       # 是否将请求方式(GET/POST...)作为资源名的一部分
      eager: true                     # 服务启动时立即注册到控制台（取消懒加载）
```

### (四) 请求限流

在控制台「簇点链路」中找到需要保护的资源，点击「流控」即可添加流控规则：

| 配置项 | 说明 |
|---|---|
| **资源名** | 受保护的接口路径，如 `/carts` |
| **阈值类型** | `QPS`（每秒请求数）或 `线程数`（并发线程数） |
| **单机阈值** | 触发限流的数值，如 QPS 为 6 表示每秒最多放行 6 个请求 |
| **是否集群** | 单机均摊或集群总体限流 |

**流控模式**

| 模式 | 说明 |
|---|---|
| **直接** | 统计当前资源的请求，超过阈值直接限流（默认） |
| **关联** | 统计与当前资源**相关的另一个资源**，当关联资源触发阈值时，限流当前资源（适用于读写冲突场景，如修改接口压力大时限流查询接口） |
| **链路** | 统计从**指定链路**访问到本资源的请求，超过阈值则限流（粒度更细，需要配合 `@SentinelResource` 并设置 `ContextUtil`） |

**流控效果**

| 效果 | 说明 |
|---|---|
| **快速失败** | 超过阈值直接拒绝，抛出 `FlowException`（默认） |
| **Warm Up（预热）** | 冷启动模式，阈值从 `阈值/coldFactor`（默认 coldFactor=3）开始，经预热时长后逐渐提升到设定阈值，保护刚启动的服务 |
| **排队等待** | 请求匀速排队通过，需设置超时时间；超时仍未处理则丢弃。适用于突发流量削峰填谷 |

### (五) 线程隔离（舱壁模式）

线程隔离有两种实现：

| 方式 | 原理 | 开销 | 代表 |
|---|---|---|---|
| **线程池隔离** | 每个业务创建独立线程池 | 大（上下文切换） | Hystrix 默认 |
| **信号量隔离** | 计数器统计当前业务使用的线程数，达到上限直接拒绝 | 极小 | **Sentinel 采用** |

Sentinel 的实现非常简单：在流控规则中把**阈值类型改为「线程数」**，设定一个业务最多能占用多少条线程。

与 OpenFeign 整合时，需要给每个 Feign 接口定义**独立的资源名**，否则所有 Feign 调用共用同一个资源，隔离就失效了：

```yaml
feign:
  sentinel:
    enabled: true     # 开启 Feign 对 Sentinel 的支持（Spring Cloud Alibaba 2021.x 及以前）
  circuitbreaker:
    enabled: true     # 新版本写法
```

```yaml
spring:
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8090
```

> 隔离的意义：即使 `item-service` 慢得离谱，`cart-service` 最多只被占用 10 条线程，其余线程仍然可以正常处理购物车其它业务。

### (六) 服务熔断

**熔断**是比限流更主动的保护手段：当被调用方出现异常时，断路器会直接"跳闸"，在一段时间内**拒绝所有对该资源的请求**，让其快速失败，避免拖垮调用方。

在控制台添加「熔断」规则：

| 熔断策略 | 触发条件 | 适用场景 |
|---|---|---|
| **慢调用比例** | 在统计时长内，请求响应时间 > 最大 RT 的比例超过设定比例 | 服务响应变慢（最常用） |
| **异常比例** | 在统计时长内，异常请求数占总请求数的比例超过阈值 | 服务频繁报错 |
| **异常数** | 在统计时长内，异常请求数量超过设定值 | 请求量较稳定的场景 |

慢调用比例规则的参数：

| 参数 | 说明 |
|---|---|
| 最大 RT | 超过该响应时间的请求计为"慢调用"，如 200ms |
| 比例阈值 | 慢调用占比的临界值，取值 `0.0 ~ 1.0`，如 0.5 |
| 熔断时长 | 熔断后拒绝请求的持续时间，如 10s |
| 最小请求数 | 统计的最小请求数量，低于该值不触发熔断，如 5 |
| 统计时长 | 统计的时间窗口，如 1000ms |

**熔断的三种状态（状态机）**

| 状态 | 行为 |
|---|---|
| **closed（关闭）** | 正常放行所有请求，并统计慢调用 / 异常比例 |
| **open（打开）** | 达到熔断条件后进入该状态，**所有请求快速失败** |
| **half-open（半开）** | 熔断时长结束后进入该状态，放行**一次探测请求**；成功则回到 `closed`，失败则重新回到 `open` |

```
        （统计指标超过阈值）
  closed ──────────────────────> open
     ↑                             │
     │        （熔断时长结束）      │
     │                             ↓
     └──── (探测请求成功) ──── half-open
                                   │
              (探测请求失败) ───────┘→ open
```

### (七) Fallback 降级

限流、熔断触发时都会抛出异常（`FlowException` / `DegradeException`），需要配合降级逻辑返回兜底数据。

**方式一：`FallbackClass`（不支持获取异常）**

```java
@Slf4j
public class ItemClientFallback implements ItemClient {
    @Override
    public List<ItemDTO> queryItemByIds(Collection<Long> ids) {
        log.error("查询商品失败，执行降级");
        return CollUtils.emptyList();
    }
}
```

**方式二：`FallbackFactory`（推荐，可捕获异常）**

```java
@Slf4j
public class ItemClientFallbackFactory implements FallbackFactory<ItemClient> {
    @Override
    public ItemClient create(Throwable cause) {
        return new ItemClient() {
            @Override
            public List<ItemDTO> queryItemByIds(Collection<Long> ids) {
                log.error("查询商品失败，异常原因：{}", cause.getMessage(), cause);
                return CollUtils.emptyList();
            }

            @Override
            public void deductStock(List<OrderDetailDTO> items) {
                // 写操作不能静默降级，应抛出异常让上层感知
                throw new BizIllegalException("库存服务不可用，请稍后重试", cause);
            }
        };
    }
}
```

注册为 Bean 后，在 `@FeignClient` 中引用：

```java
@Bean
public ItemClientFallbackFactory itemClientFallbackFactory() {
    return new ItemClientFallbackFactory();
}
```

```java
@FeignClient(value = "item-service", fallbackFactory = ItemClientFallbackFactory.class)
public interface ItemClient { ... }
```

> 降级设计原则：**查询类**接口可以返回兜底数据（空集合、缓存数据、默认值）；**写操作**不能以"成功"的姿态降级，必须抛出异常或记录待补偿任务，否则会造成数据不一致。

### (八) 规则持久化

Sentinel 的规则默认存储在**内存**中，服务重启后规则就丢失了。生产环境需要做**规则持久化**，常见方式是把规则推送到 Nacos：

## 八、分布式事务 —— Seata

### (一) 分布式事务问题

下单业务典型链路：

```
trade-service：创建订单（本地事务，写 hm-trade 库）
   ↓ 远程调用
cart-service：清理购物车（本地事务，写 hm-cart 库）
   ↓ 远程调用
item-service：扣减库存（本地事务，写 hm-item 库）
```

三个服务各有各的本地事务、各有各的数据库。如果扣库存成功但创建订单失败，购物车却已经清空了，数据就不一致了——这就是**分布式事务**问题。

### (二) 理论基础：CAP 与 BASE

**CAP 定理**（三者不可兼得）：

| 特性 | 含义 |
|---|---|
| **C - Consistency（一致性）** | 用户访问分布式系统中的任意节点，得到的数据必须一致 |
| **A - Availability（可用性）** | 用户访问集群中的任意健康节点，必须能得到响应，而不是超时或拒绝 |
| **P - Partition tolerance（分区容错性）** | 因为网络故障或其它原因，分布式系统的部分节点与其它节点失去连接，形成独立分区时，系统依然要能对外提供服务 |

分布式系统**必须满足 P**（网络分区客观存在），因此只能在 C 和 A 之间取舍：

- **CP 模式**：牺牲可用性保证一致性，等待数据同步完成后才提供服务（适用于金融、支付）
- **AP 模式**：牺牲一致性保证可用性，允许短暂的数据不一致（适用于绝大多数互联网业务）

**BASE 理论**（对 AP 模式的补充）：

| 特性 | 含义 |
|---|---|
| **Basically Available（基本可用）** | 分布式系统在出现故障时，允许损失部分可用性，保证核心可用 |
| **Soft State（软状态）** | 允许系统在一定时间内出现中间状态，如"支付中""处理中" |
| **Eventually Consistent（最终一致性）** | 经过一段时间后，所有节点的数据最终会达到一致 |

解决分布式事务的核心思路：**各个子事务分别执行和提交（AP），出现失败则通过"补偿"回滚已提交的事务**，最终达到一致。

### (三) Seata 架构

Seata 是阿里巴巴开源的分布式事务解决方案，包含三个角色：

| 角色 | 全称 | 职责 |
|---|---|---|
| **TC** | Transaction Coordinator（事务协调者） | **独立的服务（seata-server）**，维护全局和分支事务的状态，协调全局事务提交或回滚 |
| **TM** | Transaction Manager（事务管理器） | 定义全局事务的范围，负责**开始全局事务、提交/回滚全局事务**（即标了 `@GlobalTransactional` 的方法所在的服务） |
| **RM** | Resource Manager（资源管理器） | 管理分支事务，与 TC 通信，**注册分支事务、报告分支状态**，并驱动分支事务的提交或回滚 |

四个概念区分：

- **分支事务**：分布式事务中包含的每个子系统自己的本地事务
- **全局事务**：整个分布式事务，由若干分支事务组成
- **一阶段**：各分支事务**直接执行并提交**，同时记录 `undo_log`（AT 模式）
- **二阶段**：TC 根据一阶段的结果，决定全局提交（删除 `undo_log`）或全局回滚（根据 `undo_log` 反向补偿）

### (四) 四种事务模式

| 模式 | 一致性 | 隔离性 | 代码侵入 | 性能 | 适用场景 |
|---|---|---|---|---|---|
| **XA** | **强一致（CP）** | 完全隔离 | 无侵入 | 差 | 对一致性要求极高，可以接受低性能 |
| **AT** | 最终一致（AP） | 基于全局锁 | **无侵入** | 好 | **默认推荐**，绝大多数业务场景 |
| **TCC** | 最终一致（AP） | 依赖资源预留 | 侵入大（手写 Try/Confirm/Cancel） | 非常好 | 对性能要求高、需要精细控制的场景 |
| **SAGA** | 最终一致（AP） | 无隔离 | 侵入大（编写状态机与补偿接口） | 非常好 | 长事务、业务流程长且涉及多个外部系统 |

**XA 模式原理**：基于数据库的 XA 协议，一阶段不提交，只执行 SQL 并持有数据库锁；二阶段由 TC 统一通知提交或回滚。因为一直持有锁直到二阶段结束，所以一致性最强但性能最差。

**AT 模式原理**（Seata 独创，最常用）：

一阶段：
1. TM 开启全局事务，注册分支事务
2. RM 解析 SQL，查询**前置镜像（before image）**
3. 执行业务 SQL 并提交本地事务
4. 记录**后置镜像（after image）**和行锁，写入 `undo_log` 表
5. 向 TC 报告分支事务状态

二阶段：
- **提交**：异步删除 `undo_log` 与行锁记录（几乎无代价）
- **回滚**：校验脏写（对比当前数据与 after image），一致则根据 before image 生成反向 SQL 回滚；不一致则转人工处理

**TCC 模式**：需要自己写三个方法

```java
public interface AccountTCCService {
    /**
     * Try：资源的检测和预留（冻结金额）
     */
    @TwoPhaseBusinessAction(name = "deduct", commitMethod = "confirm", rollbackMethod = "cancel")
    void deduct(@BusinessActionContextParameter(paramName = "userId") String userId,
                @BusinessActionContextParameter(paramName = "money") int money);

    /**
     * Confirm：完成资源操作（真正扣款），要求必须成功，失败要重试
     */
    boolean confirm(BusinessActionContext ctx);

    /**
     * Cancel：预留资源释放（解冻金额）
     */
    boolean cancel(BusinessActionContext ctx);
}
```

使用 TCC 时必须注意三个问题：

| 问题 | 说明 | 解决 |
|---|---|---|
| **空回滚** | Try 还没执行，Cancel 就被调用 | Cancel 中判断 Try 是否执行过，未执行则直接返回成功 |
| **业务悬挂** | Cancel 比 Try 先执行，之后 Try 又执行成功，预留资源再也无人释放 | 记录事务状态，Try 执行前判断是否已回滚 |
| **幂等** | Confirm / Cancel 可能被重复调用 | 通过事务状态表保证只执行一次 |

```java
    private final CartClient cartClient;

    @Override
    @GlobalTransactional   // 开启全局事务，标记为 TM
```

### (七) AT 模式改造

使用 AT 模式需要两步改造：

**1. 在**每个参与分布式事务的业务库**中添加 `undo_log` 表**

```sql
CREATE TABLE `undo_log` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT,
  `branch_id` bigint(20) NOT NULL,
  `xid` varchar(100) NOT NULL,
  `context` varchar(128) NOT NULL,
  `rollback_info` longblob NOT NULL,
  `log_status` int(11) NOT NULL,
  `log_created` datetime NOT NULL,
  `log_modified` datetime NOT NULL,
  `ext` varchar(100) DEFAULT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `ux_undo_log` (`xid`,`branch_id`)
) ENGINE=InnoDB AUTO_INCREMENT=1 DEFAULT CHARSET=utf8;
```

**2. 修改配置**

```yaml
seata:
  data-source-proxy-mode: AT
```

**AT 模式的脏写问题与隔离性**

AT 模式一阶段就提交了本地事务（释放了**本地锁**），如果另一个非 Seata 管理的事务同时修改同一行，就可能发生**脏写**。Seata 通过 **TC 侧的全局锁**解决：

- 一阶段本地事务提交前，需要先获取**全局锁**（记录在 `lock_table`）
- 获取不到全局锁则不能提交本地事务，重试超时后**回滚本地事务**并释放本地锁
- 二阶段回滚时，会先校验 after image 与当前数据是否一致，不一致说明发生脏写，转人工处理

因此 AT 模式的默认隔离级别相当于**读未提交**。如果需要"读已提交"，可以在查询时加 `SELECT ... FOR UPDATE`（它需要先获取全局锁，从而阻塞其它分支事务的提交），并配合 `@GlobalLock` 或 `@GlobalTransactional` 使用。

### (八) 模式选型建议

| 场景 | 推荐模式 |
|---|---|
| 绝大多数普通业务（下单、扣库存、清购物车） | **AT**（无侵入、性能良好） |
| 金融、支付等要求强一致、可接受低性能 | **XA** |
| 高性能要求、需要精细控制资源（如热门商品秒杀扣减） | **TCC** |
| 业务流程很长、跨多个外部系统（如机票 + 酒店 + 租车） | **SAGA** |
| 其实能不用分布式事务就别用 | 优先通过**消息队列 + 最终一致性**或**业务拆分为可重试操作**规避 |

> 工程建议：能从业务上绕开分布式事务就绕开（如把"下单 + 扣库存"设计成 TCC 或 MQ 异步最终一致），Seata 会带来额外的锁开销、网络开销与运维成本。

### (一) 异步通信 —— MQ

同步调用链路过长会导致性能下降、级联失败风险高。通过消息队列可以把非核心链路**异步化**（如订单支付后的通知、积分、物流），实现解耦与削峰填谷。

Spring Boot 整合 AMQP 的核心用法：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>
```

```yaml
spring:
  rabbitmq:
    host: 192.168.150.101
    port: 5672
    virtual-host: /hmall
    username: hmall
    password: 123
    listener:
      simple:
        prefetch: 1                     # 每次预取 1 条，能者多劳
        retry:
          enabled: true                 # 消费者本地重试
          max-attempts: 3
    publisher-confirm-type: correlated  # 生产者确认
    publisher-returns: true
```

```java
        // 处理支付成功后的业务
    }
}
```

| 负载均衡 | **Spring Cloud LoadBalancer / NacosRule** | 轮询、随机、同集群优先 |
| 服务网关 | **Spring Cloud Gateway** | 统一入口、路由转发、断言与过滤器、统一鉴权、限流 |
| 服务保护 | **Sentinel** | 限流、线程隔离、熔断降级、热点参数防护 |
| 分布式事务 | **Seata** | XA / AT / TCC / SAGA 四种模式 |
| 异步解耦 | **RabbitMQ / SpringAMQP** | 发布订阅、可靠投递、延迟消息 |
| 分布式缓存 | **Redis** | 缓存、分布式锁、多级缓存（见 {% post_link 分布式缓存 分布式缓存 %}） |
| 部署运维 | **Docker / DockerCompose** | 容器化、一键编排 |

### (二) 一次完整请求的调用链路

以"用户下单"为例，串起所有组件：

```
1. 浏览器 ──请求带 token──> Gateway
2. Gateway：GlobalFilter 校验 JWT → 解析 userId → 写入 user-info 请求头
3. Gateway：匹配路由(/orders/**) → lb://trade-service 负载均衡 → 转发
4. trade-service：HandlerInterceptor 解析 user-info → UserContext(ThreadLocal)
5. trade-service：@GlobalTransactional 开启全局事务（TM 向 TC 注册）
6. trade-service ──OpenFeign(cart-service)──> 清理购物车（分支事务 1）
       └─ RequestInterceptor 携带 user-info 请求头
7. trade-service ──OpenFeign(item-service)──> 扣减库存（分支事务 2）
       └─ Sentinel 限流 / 熔断保护，失败走 FallbackFactory
8. 任一步失败 → TC 通知所有分支事务回滚；全部成功 → TC 通知全局提交
9. 订单创建成功 ──MQ 消息──> 后续异步流程（发券、通知、积分）
```

### (三) 关键避坑清单

| 坑 | 现象 | 解决 |
|---|---|---|
| Gateway 引入 `spring-boot-starter-web` | 启动报冲突 | 移除 web 依赖，Gateway 基于 WebFlux |
| 使用 `lb://` 但没引入 loadbalancer | `Unable to find instance` | 引入 `spring-cloud-starter-loadbalancer` |
| Nacos 2.x 未开放 9848/9849 | 客户端报连接超时 | 开放三个端口 |
| `namespace` 填了名称 | 服务互相不可见 | 必须填 ID |
| Nacos 配置的 dataId 没带后缀 | 拉取不到配置 | dataId 必须带 `.yaml` / `.properties` |
| Feign 接口参数没写 `@RequestParam` 名称 | 参数丢失 | 必须显式指定参数名 |
| Feign 返回泛型集合用 `getForObject` | `LinkedHashMap` 转换异常 | 用 `exchange()` + `ParameterizedTypeReference` |
| `@FeignClient` 不在扫描包下 | 注入失败 | `@EnableFeignClients(basePackages = ...)` |
| 配置了 Feign 日志但看不到 | 无日志输出 | 把对应包的日志级别调成 `DEBUG` |
| ThreadLocal 用完没 remove | 用户信息串号、内存泄漏 | `afterCompletion` 中必须 `remove()` |
| OpenFeign 默认不传递请求头 | 下游拿不到用户信息 | 自定义 `RequestInterceptor` |
| Seata 的 `tx-service-group` 与 `vgroup-mapping` 不一致 | `no available service` | 两者必须对应 |
| Sentinel 控制台看不到服务 | 空空如也 | 先访问一次接口，或配置 `eager: true` |
| Sentinel 规则重启丢失 | 规则没了 | 接入 Nacos 数据源做规则持久化 |

> 一句话总结：微服务的复杂度不在"拆"，而在于拆完之后**如何治理**。注册中心解决"找得到"，配置中心解决"改得动"，网关解决"进得来"，OpenFeign 解决"调得通"，Sentinel 解决"扛得住"，Seata 解决"数据对得上"。
