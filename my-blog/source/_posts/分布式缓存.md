# 分布式缓存

单机 Redis 虽然性能优异，但存在两个结构性痛点：**宕机后内存数据丢失**、**单机并发能力有上限**。围绕这两个痛点，Redis 在工程实践中形成了一条清晰的架构演进路线：

| 演进阶段 | 解决的问题 | 核心机制 |
|---|---|---|
| **持久化** | 宕机后数据恢复 | RDB 快照 / AOF 命令日志 |
| **主从集群** | 读并发上限、数据冗余 | 读写分离 + 全量/增量同步 |
| **哨兵** | 主从故障需人工切换 | 监控 + 选举 + 自动故障转移 |
| **分片集群** | 海量存储、写并发上限 | 哈希槽分片 + 集群自治 |

每一代方案都在补上一代的短板，对客户端的接入方式始终透明。下文按此顺序逐一展开。

## 一、Redis 持久化

Redis 提供 **RDB（Redis Database）** 和 **AOF（Append Only File）** 两种持久化方式，二者各有优缺点，**实际开发中通常将两者结合使用**。

### RDB

RDB 采用**定时对整个内存做快照**的方式进行持久化，触发方式包括 `save`（阻塞）、`bgsave`（后台 fork 子进程）以及配置自动触发。

- **持久化方式**：定时对整个内存做快照
- **数据完整性**：不完整，两次备份之间会丢失数据
- **文件大小**：有压缩，文件体积小
- **宕机恢复速度**：很快
- **数据恢复优先级**：低（数据完整性不如 AOF）
- **系统资源占用**：高，主要在 fork 子进程时消耗大量 CPU 和内存
- **使用场景**：可以容忍数分钟的数据丢失，追求更快的启动速度

### AOF

AOF 采用**记录每一次执行的命令**的方式进行持久化，可配置三种刷盘策略：`always`（每次写入都刷盘，最安全但最慢）、`everysec`（默认，每秒刷盘，均衡）、`no`（交给操作系统，最快但可能丢失）。

- **持久化方式**：记录每一次执行的命令
- **数据完整性**：相对完整，取决于刷盘策略
- **文件大小**：记录命令，文件体积很大（可通过 AOF 重写压缩）
- **宕机恢复速度**：慢
- **数据恢复优先级**：高（数据完整性更高）
- **系统资源占用**：低，主要是磁盘 IO 资源；但 AOF 重写时会占用大量 CPU 和内存资源
- **使用场景**：对数据安全性要求较高

### RDB 与 AOF 对比

| 对比项 | RDB | AOF |
|---|---|---|
| 持久化方式 | 定时对整个内存做快照 | 记录每一次执行的命令 |
| 数据完整性 | 不完整，两次备份之间会丢失 | 相对完整，取决于刷盘策略 |
| 文件大小 | 有压缩，文件体积小 | 记录命令，文件体积很大 |
| 宕机恢复速度 | 很快 | 慢 |
| 数据恢复优先级 | 低，数据完整性不如 AOF | 高，数据完整性更高 |
| 系统资源占用 | 高，fork 时大量 CPU 和内存消耗 | 低，主要是磁盘 IO；AOF 重写时占用大量 CPU 和内存 |
| 使用场景 | 可容忍数分钟丢失、追求更快启动 | 对数据安全性要求较高 |

### 小结
Redis 的持久化虽然可以保证数据安全，但也会带来很多额外的开销，因此持久化请遵循下列建议：
① 用来做缓存的 Redis 实例尽量不要开启持久化功能
② 建议关闭 RDB 持久化功能，使用 AOF 持久化
③ 利用脚本定期在 slave 节点做 RDB，实现数据备份
④ 设置合理的 rewrite 阈值，避免频繁的 bgrewrite
⑤ 配置 no‑appendfsync‑on‑rewrite = yes，禁止在 rewrite 期间做 aof，避免因 AOF 引起的阻塞

部署有关建议：
① Redis 实例的物理机要预留足够内存，应对 fork 和 rewrite
② 单个 Redis 实例内存上限不要太大，例如 4G 或 8G。可以加快 fork 的速度、减少主从同步、数据迁移压力
③ 不要与 CPU 密集型应用部署在一起
④ 不要与高硬盘负载应用一起部署。例如：数据库、消息队列

> 实际开发中往往**结合两者**使用：用 AOF 保障数据完整性，同时开启 RDB 在极端情况下快速恢复。生产环境常规做法为 **AOF + RDB 同时开启**，由 Redis 自行决定恢复优先级（AOF 数据更全）。

## 二、Redis 主从

单节点 Redis 的并发能力有上限，而且没有数据冗余，一旦宕机即使有持久化也存在恢复窗口。主从集群通过**读写分离**解决这两个问题：master 负责写，slave 负责读，读请求被分摊到多个从节点，master 宕机时还有 slave 充当热备。

主从同步由 `slaveof <masterIp> <masterPort>` 或 `replicaof` 命令触发，slave 与 master 建立连接后进入数据同步阶段。

### 数据同步原理

Redis 主从同步涉及两个关键标识，master 与 slave 通过它们判断彼此是否一致：

- **Replication Id（replid）**：每个 Redis 实例的唯一身份标识，相当于"数据集版本号"。master 会将自己的 replid 同步给 slave，slave 据此判断自己是否与某个 master 同步过。
- **offset**：同步偏移量，记录当前实例已同步到的字节位置。slave 通过对比自己与 master 的 offset，判断同步是否落后。

#### 全量同步的流程

主从第一次建立连接、或 slave 的 replid 与 master 不一致时，会触发**全量同步**，过程如下：

1. **slave 节点请求增量同步**
2. **master 节点判断 replid，发现不一致，拒绝增量同步**
3. **master 将完整内存数据生成 RDB，发送 RDB 到 slave**
4. **slave 清空本地数据，加载 master 的 RDB**
5. **master 将 RDB 期间的命令记录在 repl_baklog，并持续将 log 中的命令发送给 slave**
6. **slave 执行接收到的命令，保持与 master 之间的同步**

#### 全量同步和增量同步的区别

- **全量同步**：master 将完整内存数据生成 RDB，发送 RDB 到 slave。后续命令则记录在 `repl_baklog`，逐个发送给 slave。
- **增量同步**：slave 提交自己的 offset 到 master，master 获取 `repl_baklog` 中从 offset 之后的命令给 slave。

#### 什么时候执行全量同步

- slave 节点**第一次连接 master 节点时**
- slave 节点**断开时间太久**，`repl_baklog` 中的 offset 已经被覆盖时

#### 什么时候执行增量同步

- slave 节点**断开又恢复**，并且在 `repl_baklog` 中能找到 offset 时

> 一句话记忆：**能增量就增量（省资源），找不到 offset 才全量（保底）**。

### 主从集群优化

可以从以下几个方面来优化 Redis 主从集群：

- 在 master 中配置 **`repl-diskless-sync yes`** 启用无磁盘复制，避免全量同步时的磁盘 IO
- Redis 单节点上的内存占用**不要太大**，减少 RDB 导致的过多磁盘 IO
- 适当提高 **`repl_baklog` 的大小**，发现 slave 宕机时尽快实现故障恢复，尽可能避免全量同步
- **限制一个 master 上的 slave 节点数量**，如果实在太多 slave，可以采用**主-从-从链式结构**，减少 master 压力

> 主从集群遗留的问题：master 宕机后需要**人工**执行 `slaveof no one` 切换主从，期间写服务不可用——这个问题由下一节的**哨兵**解决。

## 三、Redis 哨兵

Redis 提供了**哨兵（Sentinel）机制**来实现主从集群的**自动故障恢复**。

### 哨兵的结构和作用

哨兵是一个独立的进程，部署在 Redis 主从集群之外。**通常多个哨兵组成哨兵集群**——单哨兵仍存在单点判断误判风险，多哨兵通过 `quorum` 投票达成共识才能触发故障转移，与主从的“单点 → 多点”思想一脉相承。哨兵主要承担以下三大作用：

- **监控**：Sentinel 会不断检查 master 和 slave 是否按预期工作
- **自动故障恢复**：如果 master 故障，Sentinel 会将一个 slave 提升为 master。当故障实例恢复后也以新的 master 为主
- **通知（配置中心）**：Sentinel 充当 Redis 客户端的服务发现来源，当集群发生故障转移时，会将最新信息推送给 Redis 的客户端

> 哨兵机制是 Redis 主从集群**高可用**的核心保障：监控发现问题 → 自动选举 + 故障转移 → 通知客户端切换连接，三步实现无人值守的主从切换。

### 哨兵如何监测服务状态

Sentinel 基于**心跳机制**监测服务状态，**每隔 1 秒**向集群的每个实例发送 ping 命令：

- **主观下线（SDown）**：如果某 sentinel 节点发现某实例未在规定时间响应，则认为该实例**主观下线**
- **客观下线（ODown）**：若超过指定数量（`quorum`）的 sentinel 都认为该实例主观下线，则该实例**客观下线**。`quorum` 值最好**超过 Sentinel 实例数量的一半**

> **主观下线 vs 客观下线**：主观下线只是单个 Sentinel 的判断（可能因网络抖动误判）；客观下线是多数派达成共识（去除了单点误判），**只有客观下线才会触发故障转移**。

### 选举新的 master

一旦发现 master 故障，sentinel 需要在 slave 中选择一个作为新的 master，选择依据是这样的：

- 首先会判断 **slave 节点与 master 节点断开时间长短**，如果超过指定值（`down-after-milliseconds * 10`）则会排除该 slave 节点
- 然后判断 slave 节点的 **`slave-priority` 值**，越小优先级越高，如果是 0 则永不参与选举
- 如果 `slave-priority` 一样，则判断 slave 节点的 **offset 值**，越大说明数据越新，优先级越高
- 最后是判断 slave 节点的**运行 id 大小**，越小优先级越高

> 选举顺序归纳为四道筛子：**断开时长 → 优先级 → 数据新鲜度 → 运行 id**，越靠前的条件越严格，被选中的概率越高。

### 故障转移步骤

当选中了其中一个 slave 为新的 master 后（例如 slave1），故障转移的步骤如下：

1. **sentinel 给备选的 slave1 节点发送 `slaveof no one` 命令**，让该节点成为 master
2. **sentinel 给所有其它 slave 发送 `slaveof 192.168.150.101 7002` 命令**（其中 `192.168.150.101:7002` 是新 master 的地址），让这些 slave 成为新 master 的从节点，开始从新的 master 上同步数据
3. **最后，sentinel 将故障节点标记为 slave**，当故障节点恢复后会**自动成为新 master 的 slave 节点**

> 三步故障转移：**提升新 master → 重定向其它 slave → 旧节点降级为 slave 并自动跟随**，整个过程对客户端透明，由 Sentinel 配合通知机制完成切换。

> 哨兵遗留的问题：主从+哨兵只是**数据的完整复制**（每个节点都存全量数据），既无法突破**单机内存上限**，也无法提升**写并发**——这两个问题由下一节的**分片集群**解决。

## 四、Redis 分片集群

### 分片集群结构

主从和哨兵可以解决**高可用、高并发读**的问题，但依然有两个问题没有解决：

- **海量数据存储问题**
- **高并发写的问题**

使用分片集群可以解决上述问题，分片集群特征：

- 集群中有**多个 master**，每个 master 保存不同数据
- 每个 master 都**可以有多个 slave 节点**
- master 之间**通过 ping 监测彼此健康状态**
- **客户端请求可以访问集群任意节点**，最终都会被转发到正确节点

> 总结：**主从**解决 **"读扩展 + 数据冗余"**，**哨兵**解决 **"主从自动故障转移"** ，**分片集群** 解决 **"海量数据存储 + 高并发写"** ——三者层层递进，共同构成 Redis 高可用高扩展的完整方案。

### 分片集群涉及的核心问题

下面围绕 **搭建、散列插槽、伸缩、故障转移、客户端访问** 五个核心问题展开：

#### 1. 搭建分片集群

集群中至少需要 **3 个 master** 节点（故障转移投票要求过半数）。每个节点的配置在单机基础上增加三行：

```conf
port 7001
cluster-enabled yes            # 开启集群模式
cluster-config-file nodes.conf # 集群状态文件，Redis 自动维护
cluster-node-timeout 5000      # 节点心跳超时时间（毫秒）
```

所有节点启动后，执行一条命令创建集群：

```bash
redis-cli --cluster create \
  192.168.150.101:7001 192.168.150.101:7002 192.168.150.101:7003 \
  192.168.150.102:8001 192.168.150.102:8002 192.168.150.102:8003 \
  --cluster-replicas 1
```

- `--cluster-replicas 1` 表示**每个 master 配备 1 个 slave**
- 上述 6 个节点最终形成 **3 主 3 从**的集群，master 自动平分 16384 个插槽

#### 2. 散列插槽

Redis 集群通过**散列插槽（Hash Slot）**机制决定一个 key 应该落到哪个 master 实例。

**Redis 如何判断某个 key 应该在哪个实例：**

- **将 16384 个插槽分配到不同的实例**
- **根据 key 的有效部分计算哈希值，对 16384 取余**
- **余数作为插槽，寻找插槽所在实例即可**

> "key 的有效部分"指：若 key 中包含 `{tag}` 大括号包裹的标签，则**只对 `{tag}` 内的内容**计算哈希（用于"把同一类数据打到同一实例"）；否则对**整个 key** 计算哈希。

**如何将同一类数据固定地保存在同一个 Redis 实例：**

- 这一类数据使用**相同的有效部分**，例如 key 都以 `{typeId}` 为前缀（写成 `{typeId}xxx` 的形式）。由于 `{}` 内的内容相同，哈希值相同，会被映射到**同一个插槽**，进而落到**同一个实例**

> 实战示例：把同一店铺的所有商品 key 都加上 `{shopId}` 前缀，如 `{shopId}1001:product:1`、`{shopId}1001:product:2`，这样这些 key 都会落到同一个 master 实例，方便做"按店铺聚合查询"等业务，同时也有利于运维（迁移时按 shopId 一起迁）。

#### 3. 集群伸缩

分片集群支持在**不停机**的情况下增删节点，配合插槽迁移实现弹性伸缩：

```bash
# 添加新 master 节点（默认不持有任何插槽）
redis-cli --cluster add-node 192.168.150.105:7004 192.168.150.101:7001

# 重新分片：把插槽从其它 master 迁移一部分到新节点
redis-cli --cluster reshard 192.168.150.101:7001

# 删除节点（slave 可直接删；master 必须先把插槽全部迁走）
redis-cli --cluster del-node 192.168.150.105:7004 <nodeId>
```

> 伸缩的本质是**插槽在节点间的迁移**：数据跟着插槽走，key 与 slot 的映射关系始终不变，因此对业务无感。

#### 4. 故障转移

分片集群**不再需要哨兵**，master 之间通过 ping 彼此监测，故障转移由集群内部自治完成：

- 某节点发现 master 无响应 → 标记其为疑似下线（PFAIL）并广播
- **超过半数的 master 都标记该节点下线（FAIL）** → 触发故障转移
- 该 master 下的 slave 发起选举，**获得超过半数 master 支持的 slave** 当选为新 master
- 客户端收到 MOVED 重定向，自动切换到新 master

**手动 Failover（数据迁移）**：利用 **`cluster failover` 命令**可以手动让集群中的某个 master 宕机，切换到执行该命令的 slave 节点，实现**无感知的数据迁移**（例如计划性维护、替换节点）。

流程图（6 步）：

```
 slave                          master                        其它 master
   │                               │                              │
   │ ① 请求暂停服务                │                              │
   │  （slave 拒绝客户端请求）────▶ │                              │
   │                               │                              │
   │ ◀──────── ② 返回当前 offset ─ │                              │
   │                               │                              │
   │ ③ 等待自身 offset 追平 master │                              │
   │                               │                              │
   │ ④ 发起故障转移 ─────────────▶ │                              │
   │                               │                              │
   │ ⑤ 标记自己为 master，广播故障转移结果 ─────────────────────▶ │
   │                               │                              │
   │ ⑥ 开始处理客户端读写请求      │                              │
```

手动的 Failover 支持三种不同模式：

| 模式 | 行为 |
|---|---|
| **缺省** | 默认的流程，如上图 1~6 步 |
| **force** | 省略了对 offset 的一致性校验 |
| **takeover** | 直接执行第 5 步，**忽略数据一致性、忽略 master 状态和其它 master 的意见**（最暴力，可能丢数据） |

> **使用建议**：日常运维优先使用**缺省**模式；确认 master 已彻底不可用、想快速接管时用 **force**；**takeover 仅用于极端场景**，可能造成数据丢失，慎用。

#### 5. RedisTemplate 访问分片集群

Spring Data Redis（Lettuce 客户端）原生支持分片集群，只需把配置从单机连接改为集群节点列表：

```yaml
spring:
  data:
    redis:
      cluster:
        nodes:
          - 192.168.150.101:7001
          - 192.168.150.101:7002
          - 192.168.150.101:7003
          - 192.168.150.102:8001
          - 192.168.150.102:8002
          - 192.168.150.102:8003
```

- 底层 Lettuce 会自动根据哈希槽计算 key 的归属节点，并处理 **MOVED / ASK 重定向**
- **业务代码零改动**：`RedisTemplate` 的用法与单机完全一致，读写分离、故障切换对开发者透明

## 五、总结

| 方案 | 解决的问题 | 核心机制 | 遗留问题 |
|---|---|---|---|
| **持久化** | 宕机数据丢失 | RDB 快照 / AOF 命令日志 | 单机并发上限 |
| **主从** | 读并发上限、冗余 | 读写分离 + 全量/增量同步 | master 故障需人工切换 |
| **哨兵** | 自动故障转移 | 监控 + 选举 + 故障转移 | 每节点存全量数据，存储与写并发受限 |
| **分片集群** | 海量存储 + 高并发写 | 哈希槽分片 + 集群自治 | —（运维复杂度上升） |

> Redis 高可用架构的演进逻辑：**每一代方案在解决上一代遗留问题的同时，都保持对客户端的透明性**——从 RDB/AOF 的自动恢复，到主从的读写分离，到哨兵的无人值守切换，再到分片集群的弹性伸缩，开发者始终只需面对一个“稳定的 Redis”。

> 至此，单机 Redis 的“数据丢失”与“并发上限”两大痛点被完全闭环。当业务继续发展、面临异地多活、限流风控等更高要求时，可进一步引入 Redis Cluster Proxy、Codis、Twemproxy 等中间层，或在客户端层做更精细的流量治理。
